# 투고 요청 P-0001 (받은 그대로)

> 2026-11-25 학회장(메인 대화 세션)이 저자에게 보낸 지시서 전문이다. 고치지 않고 옮겼다(맨 위 한 줄도 받은 글의 일부).

---

이 지시서에 적힌 의도·대상·제약을 바탕으로 작업하세요. 선택값은 분류·기록용이며 실제 작업 내용·범위·순서는 아래 구체적인 지시를 따릅니다.

## 배경 설명
[투고 요청 P-0001] — 학회장(메인 대화 세션)이 저자에게 보내는 글. 이 양식(1 질문 · 2 문제 의식 · 3 재료 · 4 지킬 규칙 · 5 낼 것 · 6 하지 않을 것 · 7 심사에서 볼 것 · 8 끝났을 때 보고) 자체가 시범이고, 사용자가 결과를 보고 채택할지 정한다.

■ 이 일이 무엇인가
stock-rader는 Claude가 혼자 가상 투자를 하며 '논리 조각'을 쌓는 실험이다(루트 CLAUDE.md를 먼저 읽는다). 사용자가 2026-11-25에 새 방식을 시범으로 해 보자고 했다: 한 에이전트(저자)가 기록을 보고 '이런 것 같다'는 논문을 쓰고, 다른 에이전트(심사자, 다른 모델)가 비판한다 — 논문과 동료 심사. 너는 첫 논문의 저자다.

사용자 말(2026-11-25, 요지):
- "과적합이 돼도 과거 실제 경험들로 테스트 해보는 게 중요하다. 미래는 몰라도 이미 일어났던 일에는 논리가 맞아야 적절한 논리다."
- "과학도 일종의 과적합 문제가 있지만, 가장 잘 설명하는 이론을 채택하고 예외를 만든다. 반박은 결국 과거의 사례를 끌고 오는 것이고, 그 사례가 적으면 예외로 설명한다."
- "과학은 시기에 상관이 없지만 주식은 시기가 중요하다." → 시기는 '판단 때 잴 수 있는 조건'으로 적고, 여러 시기의 사례에 대 본다.
- 이론은 '내일 오른다'가 아니라 '이런 조건일 때 이 기한 동안 결과가 이쪽으로 기운다' 꼴이다. 기한은 저장소가 쓰는 1·5·20 거래일 안에서 고른다(확인하기 힘든 긴 기한은 쓰지 않는다).

■ 1. 질문
"이 계좌가 크게 잃은 날과 주에는, 판단하던 때 미리 잴 수 있던 조건이 있었나?"
질문만 준다. 가설(어떤 조건인가)은 네가 기록을 보고 세운다. 답이 '없었다'여도 논문이다 — 그때는 무엇을 대 봤고 왜 아닌지를 쓴다.

■ 2. 문제 의식
- 큰 주제는 '돈을 잃지 않으려면 어디에 넣어야 하나'다. 답이 그냥 '현금'이 되지 않으려면 먼저 '언제 크게 잃는지 미리 알 수 있나'를 알아야 한다.
- 기록에서 나온 문제: 2026-11-16·11-20·11-23처럼 크게 빠진 날의 돌아보기가 대부분 '바깥 상황'(판단 때 알 수 없던 일)으로 분류됐다. 한 조각(Q_margin_relief)은 틀린 11건 중 10건이 바깥 상황이다. 정말 알 수 없었는지는 아무도 따져 보지 않았다.
- 1단계 재생(docs/replay-2026-07-10.md)에서도 시세 모양 조각만으로는 시기가 바뀌는 것을 못 알아봤다.

■ 3. 재료
쓸 수 있는 것(모두 읽기만):
- records/account.jsonl(계좌 넷, 1기와 2기 `@2`), prediction·score·review·lesson·order·fill
- records/reading.jsonl(대상별 시세 조건 값과 숫자), hand_reading.jsonl(그날 조사 조건 값과 까닭), research.jsonl(조사 답, 2026-11-05부터 numbers·as_of), reading_check.jsonl(조사 조건 값을 나중에 다시 확인한 것), premarket·scan(11-18부터)
- data/prices/(끝난 일봉, 여러 해 치) — 시세로 재는 조건을 여러 해·여러 시기에 대 볼 때
- knowledge.toml, lessons.toml, 읽기 전용 명령 `python -m market.breakdown <조각 id>` 등(루트 CLAUDE.md '구조와 명령')
쓰면 안 되는 것:
- 지금 웹 검색으로 지난 날의 조건 값을 새로 만드는 것(결과를 아는 기사가 섞인다). 조사 조건은 그날 기록된 값만 쓴다.
- 조사 답의 글을 네가 읽고 예/아니오를 새로 매기는 것(결과를 아는 채 읽게 된다). 새 조건이 필요하면 숫자 문턱을 먼저 적고, 기록된 숫자에서 코드가 값을 꺼내게 한다.

## 작업 1: 분석

위 질문에 답할 분석을 한다. 순서:
(1) '크게 잃었다'의 뜻을 자료를 자세히 보기 전에 먼저 정해 적는다(어느 계좌, 하루·1주, 문턱과 그 까닭). 정한 뒤에 바꾸면 바꿨다고 적고, 다른 문턱 둘로도 결과가 같은 쪽인지 같이 보인다.
(2) 후보 조건을 여럿 세운다(적어도 셋, 서로 다른 종류로 — 예: 시세로 재는 것, 그날 기록된 조사 조건, 계좌 자신의 상태인 몰림·비중). 후보마다 '판단 때 잴 수 있었나'를 값의 시각으로 확인한다.
(3) 후보마다 우리 기록의 모든 날에 대 본다 — 크게 잃은 날만이 아니라 잃지 않은 날, 조건이 켜졌는데 잃지 않은 날까지. 같은 사건·겹치는 기간은 한 건으로 묶은 수(독립 사례)를 같이 센다(lessons.toml L09).
(4) 시세로 재는 후보는 data/prices의 여러 해 치에도 대 본다(계좌 대신 세 대상 또는 같은 비중으로 든 묶음의 움직임으로). 시기를 나눠(오르는 때·내리는 때·흔들림 큰 때 등, 나누는 잣대와 까닭을 적는다) 시기마다 성적을 따로 낸다. 어느 시기에나 맞는지, 한 시기에서만 맞는지 가른다.
(5) 후보들을 한 잣대로 견줘 가장 잘 설명하는 것을 고른다(잣대는 네가 정하고 까닭을 적는다 — 예: 설명한 독립 사례 수, 예외 수, 조건 개수, 조건 없이 그냥 찍었을 때와의 차이). 남는 사례는 예외로 적되 예외가 많으면 그 후보는 채택하지 않는다.
(6) 앞으로의 판정 계획을 미리 적는다: 어떤 기록이 몇 건(독립) 모이면 언제 판정하고, 어떻게 나오면 버리는지.

  7. 판정 계획 — 앞으로 무엇이 몇 건 모이면 언제 판정, 버릴 조건

## 구체적인 지시·기본 확인
■ 4. 지킬 규칙
- 조건은 판단하던 때 잴 수 있던 것만. 값의 시각(known_through·as_of·run)으로 확인하고, 판단 뒤에 나온 값이 하나라도 섞이면 그 후보는 버린다.
- 맞은 날·잃지 않은 날까지 전부 대 본다. 틀린 날만 보고 조건을 정하지 않는다.
- 같은 사건은 한 건. 독립 사례 수를 늘 같이 적는다.
- 해 본 후보는 버린 것까지 전부 적는다(좋은 것만 내지 않는다).
- 과거 사례에 맞는 것은 '채택 시험'이지 성적이 아니다. 성적은 세운 뒤의 날들로만 센다(저장소 규칙 '가설만 있다'). 논문에 '검증됨'이라고 쓰지 않는다.
- 숫자에는 까닭을 붙인다. 문턱은 네가 정하되 정한 까닭과 다시 볼 기준을 적는다.
- 공개 저장소다: 비밀값·개인 정보·기사 본문을 두지 않는다.
- 2026-06까지의 시세 결과는 네가 이미 알 수 있는 기간이다. 조건 값은 코드가 시세에서 계산하게 하고, 네 기억으로 시기를 고르지 않는다.

■ 6. 하지 않을 것
- `records/`·`reports/`·`data/prices/`·`knowledge.toml`·`lessons.toml`·`docs/routine-*.md`·`market/`을 고치지 않는다(읽기만). 새로 쓰는 곳은 `papers/`뿐이다.
- 논리집에 조각을 세우지 않는다(채택은 심사 뒤 학회장이 정한다).
- push하지 않는다. 네 작업 폴더의 브랜치에 커밋만 한다.
- 웹 검색으로 지난 날의 값을 채우지 않는다.

■ 7. 심사에서 볼 것 (미리 알림 — 심사자는 다른 모델이고 네 설명보다 기록을 먼저 본다)
① 다시 계산하면 같은 숫자가 나오나 ② 조건 값이 정말 판단 때 알 수 있던 것인가 ③ 네가 안 가져온 과거 사례 가운데 반대되는 것이 있나 ④ 잡음이나 시장 전체가 같이 움직인 몫으로도 설명되지 않나 ⑤ 사례 수에 견줘 조건이 너무 많지 않나 ⑥ 후보를 전부 적었나.

■ 8. 끝났을 때 보고 (마지막 답에 이 다섯 줄)
- 답: 있었다/없었다/모른다 + 주장 한 문장
- 증거: 우리 기록 독립 사례 N건 중 설명 n·예외 m / 과거 시세 시기별 한 줄
- 해 본 후보 수와 고른 까닭 한 줄
- 확인한 것(evidence.py 종료 0, `python -m market.records check` 통과)·확인 못 한 것
- 양식에서 불편했던 곳

■ 완료 기준
`python papers/P-0001/evidence.py`가 종료 0으로 돌고 논문의 숫자와 같다. `python -m market.records check`와 `python -m unittest discover -s tests -t .`가 시작 전과 같이 통과한다(네가 기록을 안 건드렸다는 확인). 한글이 깨지면 `PYTHONIOENCODING=utf-8`.

## 제작 후 별도 검토
범위: 전체
검토 단계: 4단계
검토 방식: 읽고 판단 / 테스트 실행

동료 심사(사용자가 Gemini 4단계로 보낸다). 저자의 설명보다 기록을 먼저 본다. 의견이 아니라 계산과 반례로 말한다. 심사서 양식 — [심사 P-0001] 1. 다시 계산: `python papers/P-0001/evidence.py`를 돌려 논문 숫자와 같은지(다른 곳 목록) 2. 판단 때 알 수 있었나: 조건 값의 시각을 기록에서 확인(섞인 곳 목록) 3. 반례: 저자가 안 가져온 과거 사례(우리 기록·data/prices) 가운데 주장과 반대되는 것을 직접 찾아 날짜와 숫자로 4. 다른 설명: 잡음·시장 전체 몫·문턱을 조금 바꿨을 때도 서는지 5. 과적합 정도: 독립 사례 수 대 조건 수, 해 본 후보 수 6. 빠진 것: 사례 전체 표·버린 후보·예외·판정 계획 7. 판정: 채택 / 고쳐서 다시(고칠 것 목록) / 거절 — 까닭 한 문단 8. 양식에 대한 말. 심사자는 파일을 고치지 않는다.

이는 별도 검토 계획입니다. 검토자는 사용자가 작업자 카드에서 보내며, 이 지시로 자동 생성되지는 않습니다.
