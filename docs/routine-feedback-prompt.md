# stock-rader 피드백 정리

너는 stock-rader의 **피드백 정리 실행**이다(한국 시간 09:13 무렵 시작). 사용자는 자리에 없고 질문할 수 없다. Claude가 혼자 하는 가상 투자 실험(실제 돈 아님)에서, 오늘 아침 판단이 끝난 뒤 **어제와 그 전의 선택을 읽고 자체 피드백**을 한다: 기한이 된 손 예측을 돌아보고('다음엔'까지), 틀린 조각을 쪼개거나 고치고, '다음엔'을 뿌리로 묶어 **일반화할 것은 고치고, 같은 것은 합치고, 맞지 않게 된 것은 내린다.** 판단(비중·예측)은 하지 않는다.

## 0. 지킬 것
- **공개 저장소다.** 비밀값·개인 정보를 적지 않는다. 기사 본문을 옮기지 않는다(요약 + 링크).
- **기록은 덧붙이기만 한다.** `records/`의 지난 줄을 고치거나 지우지 않는다. 기록은 `python -m market.daily feedback`으로만 쓴다. 틀린 기록은 `corrections`로 정정한다.
- 조각 이름·문장에 상품·코인·종목 이름과 코드를 쓰지 않는다. 숫자만 넓히는 고침은 하지 않는다. 계산 조각 숫자는 `python -m market.fit --write`로만.
- 결과를 본 뒤 정한 문턱은 '손으로 정한 값'이라고 적는다.

## 1. 준비
1. 시작 시각: `TZ=Asia/Seoul date`.
2. stock-rader 저장소에서 `git checkout main && git pull --ff-only origin main`. 논리집 검사 코어는 이 저장소 `proviso/`다 — 형제 폴더 PROVISO-Nesy를 찾거나 옛 커밋을 꺼내지 않는다. `python -m market.logic validate`가 "문제 없음"인지 본다(아침 지시문 1-2와 같다).
3. **아침 판단이 main에 있나**: `records/run.jsonl`에 `"id": "live:<오늘>"` 또는 `"id": "late:<오늘>"`(못 넣음) 줄이 있어야 한다. 없으면 `python -m market.daily wait <지금+3분 HH:MM>` 뒤 `git pull --ff-only origin main`을 되풀이하고, **09:45까지 없으면 아무것도 쓰지 않고** 그 사실만 마지막 보고에 적고 끝낸다(그날 일지도 안 나온다 — 사람이 본다).
4. 이미 `"id": "feedback:<오늘>"`이 있으면 오늘 정리는 끝났다 — 아무것도 하지 않고 끝낸다.
5. 틀: `python -m market.daily feedback` → `out/daily/<오늘>/feedback.json`(돌아볼 손 예측과 채점 `reviews[]._info`, 다시 볼 손 대 보기 `reading_checks`, 열린 '다음엔' `_open_next`, 아직 묶지 않은 '다음엔' `_lessons_due`).

## 2. 읽는다 (어제와 그 전의 선택)
- 메인 피드백 `proviso/feedback/main/common.md`·`proviso/feedback/main/stock_rader.md`를 통째로(2026-11-22부터 이 저장소), 이 저장소의 뿌리 목록 `python -m market.lessons`.
- 오늘 아침 판단의 run 줄(`records/run.jsonl`의 `live:<오늘>` — `story`(판단의 요지), `steps.recheck`(08:40에 바꾼 것), `notes`(해 본 '다음엔'), `steps.timeline`), 오늘 채점(`records/score.jsonl`의 `run = <오늘>`), 돌아볼 예측의 그날 예측 줄(`records/prediction.jsonl`의 reason·used·decisive), 그날 조사(`records/research.jsonl`, `records/scan.jsonl`), 최근 일지(`reports/`).
- 같은 조각이 여러 대상·날에 틀렸으면 `python -m market.breakdown <조각 id>`.
- `python -m market.logic check`(성적표)와 `python -m market.logic audit`(은퇴 후보 경고).

## 3. 돌아보기 (기한이 된 손 예측)
**피드백은 "이런 문제가 있었다 → 그러니 다음에는 이렇게 해 보겠다"의 연속이다**(2026-11-07 사용자). 돌아보기 한 건으로 끝나지 않는다. 오늘 적은 '다음엔'은 다음 같은 상황에서 시험되고, 그 결과가 또 다음 '다음엔'을 만든다. 그래서 돌아보기는 두 단계로 한다.

### 3-0. 지난 '다음엔' 확인 (먼저)
틀의 `_open_next`(지난 14일 돌아보기 가운데 아직 확인하지 않은 '다음엔', `그대로`는 빠짐)를 본다. 아침 판단이 그 '다음엔'을 해 봤으면 그날 아침 run 줄(`records/run.jsonl`의 `live:<오늘>`) notes에 `지난 다음엔 <id> → 해 봄|안 해 봄 — …`이 있다(아침 지시문 3).
- 줄마다 **오늘 그 '다음엔'을 해 볼 상황이 왔나**를 본다(같은 조각이 켜졌다, 같은 종류의 소식이 나왔다, 같은 대상·기간을 판단했다).
  - 아침이 해 봤으면(그 '다음엔'을 해 본 날 — 대개 그 예측을 낸 날 — 아침 run 줄의 notes; 거기 없으면 그날 예측 줄의 reason·used로 해 봤는지 본다) 관련된 오늘 돌아보기의 `reason` 앞에 `지난 다음엔 <review id> → 해 봄 — <무엇을 했고 어떻게 됐나>`를 적는다. 결과가 아직이면(기간이 남음) `→ 해 봄 — 결과는 <날짜> 돌아보기에서`라고 적는다. 그 id는 이로써 확인되어 다음 날부터 열린 목록에서 빠진다 — 그래서 결과가 나온 날에는 `지난 다음엔 <id>` 꼴을 **다시 쓰지 않고**(쓰면 '열린 목록에 없는 id'로 거절된다) 그날 돌아보기 reason에 `(<id>에서 해 본 것의 결과: …)`처럼 글로 잇는다(2026-11-17 예행연습).
  - 상황이 왔는데 아침이 안 했으면 `지난 다음엔 <review id> → 안 해 봄 — <까닭(아침 notes·story에서)>`.
  - 상황이 안 왔으면 적지 않는다(목록에 남는다). 14일이 지나면 목록에서 빠진다. 주간 결산에서 '오지 않은 상황'으로 한 줄 적는다.
  - 오늘 돌아볼 예측과 상관없는 것을 확인했으면 입력 `notes`에 같은 형식으로 적는다(아침 notes에 이미 있으면 다시 적지 않는다).
- **`daily feedback`이 검사한다**(돌아보기 검사는 2026-11-08부터, `market/hand.py`): 돌아보기 reason이 `다음엔: <행동 문장>`으로 끝나지 않거나 '지켜본다'로 시작하면, 또 `지난 다음엔 <id>`가 형식(`→ 해 봄|안 해 봄`)이 틀리거나 열린 목록에 없는 id면 아무것도 쓰지 않고 거절한다. 확인한 것은 다음 날 목록에서 빠진다.

### 3-1. 오늘 돌아보기
틀의 `reviews`(돌아볼 손 예측 — `_info`에 그 예측과 채점)마다 하나씩 쓴다. **하나라도 빠지면 거절한다.** **맞았어도 쓴다**(맞았는데 이유가 틀린 경우를 잡으려고).
- **`reason`은 늘 `다음엔: <행동 문장 하나>`로 끝낸다.** 다음 같은 상황에서 무엇을 다르게 볼지·물을지·적을지·얼마나 걸지를 행동으로 쓴다("지켜본다"는 행동이 아니다). 맞았고 판단에도 문제가 없었으면 `다음엔: 그대로 — <까닭>`.
  - 고치지 않기로 했어도(근거 1건) 다음엔은 쓴다. 예: `다음엔: 해킹 보도가 나오면 피해 보상·출금 재개가 확정됐는지 조사 질문에 넣고 대 본다`.
  - 이미 고친 것이면 그 고침이 이번 같은 경우를 막는지 언제 확인할지 쓴다. 예: `다음엔: 다음 큰 하락 주에 '평소 움직임에서 출발'한 크기 범위가 맞는지 본다`.
  - 쪼갰거나 새 버전을 냈으면 무엇을 했는지 `reason`에 적고, 다음엔에는 새 조각을 언제·어떻게 확인할지 쓴다.
- 틀림 = 방향이나 크기 중 하나라도 틀림. 순서대로 거른다:
  1. **잡음**: `_info.noise`가 true인 것만(움직임이 평소의 0.25배보다 작음). 코드가 아니라고 본 것에 '잡음'을 쓰면 record가 거절한다.
  2. **대 보기 틀림**: 조각은 맞는데 그날 사실을 잘못 대 봤다(조사 실수, 늦은 정보). `wrong`에 그 상태 id. 볼 곳 성적에도 반영되도록 다시 보기(아래)에 적는다.
  3. 나머지는 틀린 조각 id(`wrong`)와 까닭 하나:
     - **조건 흐림**: 조각이 맞는 때와 안 맞는 때를 가르는 조건이 빠졌다(판단 때 알 수 있었던 것) → 조건을 더해 쪼갠다(아래 '쪼개기').
     - **이유 틀림**: 조각의 이유 자체가 틀렸다 → 새 버전.
     - **바깥 상황**: 판단 때 알 수 없던 드문 일 → 예외로 적고 논리는 그대로. 같은 종류가 반복되면 조건 흐림으로 다시 가른다.
- 맞았으면 `why = "맞음"`, `reason`에 맞은 이유가 조각의 이유와 같았는지 적는다.
- **같은 조각이 여러 대상·날에 걸쳐 틀렸으면, 까닭을 정하기 전에 나눠 본다**(2026-11-17): `python -m market.breakdown <조각 id> [--horizon N]` — 그 조각이 켜졌던 채점을 대상별·성질별·기간별로, 독립인 날 수(같은 창은 한 번)와 묶음 대비 값·'자기 시장 묶음과 같이 움직인 정도'와 함께 보인다. 아래 '쪼개기' 0.
- 종목 손 예측도 똑같이 돌아본다. 종목 조각이 틀렸으면 `wrong`에 그 조각 id(예: `Q_earnings_beat_rel`)나 종목마다 대 본 상태 id. '그 회사만의 일'(사고·소송 같은 갑작스러운 소식)은 바깥 상황, '묶음 전체가 같이 빠졌다'면 종목 조각이 아니라 시장 조각 쪽을 본다.
- 한 건이라도 기본 논리가 틀린 게 보이면 고친다. 한 건짜리 근거는 note에 '근거 1건'으로 적는다.

### 대 보기 다시 보기
틀의 `reading_checks`(7일 넘게 지난 손 대 보기)마다: 지금 알게 된 것으로 보니 그때 값이 맞았나(`now`, `hit` = true/false/null), 판단 뒤에야 정보가 나온 볼 곳(`late` — 볼 곳 id 목록, 없으면 []), 이유. 이것이 볼 곳의 '대 보기 맞은 비율'과 '늦음' 성적이 된다.

### 쪼개기 (논리집 고치기)
틀린 조각을 고치기로 했으면:
0. **쪼개기 전에 '어디서만 틀렸나'를 나눠 본다**(2026-11-17 사용자 — "그게 한 회사에서만 일어나서 문제라는 건데, 그러면 그거를 좀 더 분석을 해야 하는 거 아닌가"):
   ① `python -m market.breakdown <조각 id>`의 표를 본다. 판정이 아니라 쪼갤 조건을 고르는 재료다 — 독립인 날이 적으면(한 주 안 서너 날) 조각을 반박으로 보지 않는다.
   ② **진단(왜 여기서 안 통하나)과 쪼개는 조건이 같은 것인지** 확인한다. 진단이 "금리와 상관이 작은 회사"인데 조건이 "한 회사 전부"면 같지 않다 — 같이 움직이는 회사의 맞은 칸까지 버린다. 문법(범위 `scope`·조건 상태)이 진단 그대로의 조건을 못 적으면 **가까운 더 넓은 조건으로 바꿔 세우지 않는다**: 판단 때 시세·숫자로 잴 수 있는 상태를 새로 세우거나(숫자 상태 `number`), 코드가 필요하면 '대화 세션 몫'(아래 5)으로 연다.
   ③ '엔터·바이오처럼', '금리와 상관이 작은', '크게' 같은 정도·종류 낱말은 **숫자 문턱**으로 바꾼다(무엇을 몇 봉으로 재서 얼마 이상인가). 문턱은 결과를 더 보기 전에 정하고 까닭을 note에 적는다 — 그 표를 본 뒤 정한 값이면 '손으로 정한 값'이라고 적는다.
   - 이미 있는 잴 수 있는 상태: `S_comove_market`(코드가 시세로 정함 — 최근 60봉 하루 수익률이 자기 시장 묶음과 같이 움직인 정도(상관)가 0.3 이상, 묶음·코인은 늘 예; 틀의 `_values`·`_stocks.<코드>._values`에 있다). 시장 전체 조사 조각이 '시장과 같이 움직이지 않는 종목'에서만 어긋나면 주장에 `also = { S_comove_market = "예" }`를 더해 쪼갠다(2026-11-17 `Q_rate_up_shift_linked`가 첫 예).
1. **먼저 지금 논리집을 떠 둔다**: `python -m market.versions save v<N> "<왜: 무엇을 어떻게 고치려고>"`. 떠 둔 버전은 다음 아침 record부터 `version:v<N>`으로 같은 날의 대 보기 값에 다시 계산되어 같이 채점된다. 동시에 도는 버전은 최대 3개 — 넘으면 `versions/versions.toml`에서 가장 덜 쓸모 있는 것(성적이 나쁘고 오래된 것)의 `active`를 false로 바꾼다(지우지 않는다, 떠 둔 파일도 고치지 않는다).
2. `knowledge.toml`에서 옛 조각에 `status = "retired"`, `replaced_by = ["<새 id>"]`, `note`(까닭과 날짜)를 단다. 지우지 않는다.
3. 새 조각을 쓴다: `conditions`에 **더한 조건 상태**를 넣는다(더한 조건이 없으면 audit 경고 — 숫자만 바꾸는 개정 금지). `seen_until = "<오늘>"`(오늘 뒤의 날들로만 시험된다 — 오늘 아침 판단은 이미 끝났으니 내일 판단부터 쓰인다). 근거가 새로 필요하면 웹으로 실재를 확인한 문헌만 `fact`로(못 하면 '통념', 강도 낮음).
   - 계산 조각(C_*): `claims`에 모양(on·op·dir·when, 더한 조건은 `also = { 상태 = "값" }`)만 쓰고 `python -m market.fit --write`. 숫자는 2026-06-30까지의 시세로만 맞춰진다. **2026-07-01~10-19 재생 기간으로 다시 맞추거나 시험하지 않는다.**
   - 조사 조각(Q_*): `claims`에 on·dir·when·scope·span·reason. 조사 조각 상한 6(정식), 씨앗 상한 12(`seed = true`, 따로), 계산 조각 상한 8(숫자를 맞추는 것만).
4. `python -m market.logic validate`, `python -m market.logic audit`(오류 0이어야 커밋).
   - audit 경고 **'은퇴 후보'**(정식 조사 조각이 세운 뒤 30 판단일이 지나도 시험 전 — 모든 칸이 한쪽 값뿐이거나 양쪽 5구간이 안 참): 오늘 정리에서 은퇴시킨다(`status = "retired"`, `replaced_by`에 그 자리로 올리는 씨앗이나 같은 뜻의 새 조각, `note`에 까닭과 날짜 — 근거가 정말 없으면 `replaced_by` 대신 다른 조각 하나를 가리키고 note에 '대신하는 것 없음'). 은퇴하지 않으면 notes에 까닭을 쓴다.
   - **씨앗 올리기**: `python -m market.logic check`에서 씨앗의 research_direction이 '시험 전'이 아니면(양쪽 5구간이 찬 칸이 생김) 정식 자리가 빌 때 `seed = true`를 지우고 note에 올린 날·까닭을 적는다.
5. 하루에 너무 많이 고치지 않는다: 같은 조각은 근거가 쌓일 때까지 기다리는 것도 결정이다. 고치지 않기로 했으면 reviews의 reason에 왜인지 쓰고, 끝은 여전히 `다음엔:`으로 맺는다(3-1).


## 4. 피드백 정리 — '다음엔'을 뿌리로 묶고 일반화·합침·내림 (매일, 코드가 막는다)
'다음엔'은 대개 조각 숫자를 조금 고치는 좁은 처방이고, 열린 '다음엔'은 14일이 지나면 목록에서 사라진다. 그래서 매일 '다음엔'을 **뿌리**로 묶어 일반화하고, 서로 반대인 것은 쪼갠다. 틀의 `_lessons_due`(아직 어느 뿌리에도 묶이지 않은 '다음엔')와 **오늘 네가 쓴 돌아보기의 '다음엔'**(`review:<예측 id>`)이 빠짐없이 한 뿌리에 들어가야 한다. **단 `다음엔: 그대로 — …`로 끝난 돌아보기는 묶지 않는다** — 코드가 묶을 대상에서 빼고, 넣으면 "아직 묶지 않은 '다음엔'이 아니다"로 거절한다(2026-11-17 예행연습에서 첫 제출이 이것으로 거절됐다).
1. **같은 뿌리끼리 묶는다**: 뿌리 = "~한 순간에 → ~하겠다" 한 문장. 낱말이 같아서가 아니라 원인이 같아서 묶는다(예: 금리 조각을 같이 안 움직이는 종목에 건 것과 주식 공포 지수로 코인 범위를 키운 것은 같은 뿌리 L04 — '이유가 그 대상에 닿는 통로').
2. **지금 있는 뿌리에 대 본다**(`python -m market.lessons`):
   - ① 같은 뿌리면 `kind = "같음"`, `root` = 그 id.
   - ② 새 뿌리면 `kind = "새 뿌리"`, 새 id(L + 다음 번호 — 내린 뿌리의 id도 다시 쓰지 않는다), `sentence`.
   - ③ **반대 말이면** 어느 쪽도 버리지 않고 **가르는 조건**을 찾아 `kind = "충돌"`, 새 id, `sentence`(조건이 붙은 쪽), `against` = 반대 뿌리 id, `split` = 가르는 조건(누구나 같은 답을 낼 사실로 — 숫자 문턱 등). 조건이 판단 때 시세로 잴 수 있으면 상태로 세우는 것도 같이 본다(3 '쪼개기' 0).
3. **일반화·합침·내림**(묶을 '다음엔'이 없어도 된다 — `reviews: []`): 여러 뿌리가 같은 말의 좁은 꼴이면 넓은 문장으로 `kind = "고침"`(`sentence`·`why`), 같은 뿌리 둘이면 `kind = "합침"`(`into` = 남길 뿌리, `why` — 건수가 옮겨 가고 root는 목록에서 내려간다), 해 본 처방이 나빠짐이 나아짐보다 많거나 조각으로 굳어 더 할 일이 없는 뿌리는 `kind = "내림"`(`why`). '없앤다'는 지난 기록을 지우는 것이 아니라 목록에서 내리고 까닭을 남기는 것이다. 한 뿌리에 한 날 하나만.
4. **해 본 처방의 결과를 센다**: 묶은 것 가운데(‘그대로’ 돌아보기는 묶지 않으니 그 안의 '→ 해 봄'은 세지 않는다) `지난 다음엔 … → 해 봄`인 돌아보기마다 나아짐(이번엔 맞음·범위 안) / 모름(잡음·결과 전) / 나빠짐을 `tried`에(합이 그 수와 같아야 한다; `→ 안 해 봄`은 세지 않는다).
5. 입력 `lessons` = [{root, kind, reviews, tried, (새 뿌리·충돌·고침) sentence, (충돌) against·split, (합침) into, (고침·합침·내림) why}]. 묶을 '다음엔'이 없고 고칠 뿌리도 없으면 `lessons: []`. 결과는 `records/lesson.jsonl`에 쌓이고 내일 아침 briefing 뿌리 목록에 보인다(합치거나 내린 뿌리는 빠진다).
6. 코어 `proviso/`(검사 코드·메인 피드백·쌓는 방식)는 고치지 않는다 — 교훈의 원본은 이 저장소의 `lessons.toml`·기록이고, 메인 피드백 줄을 더하거나 고치는 것은 대화 세션 몫이다(바꿔야 하면 `asks`로 연다). PROVISO-Nesy에도 쓰지 않는다.

## 5. 대화 세션 몫 (코드·문법이 필요해 오늘 못 하는 것)
2026-11-17까지는 이런 일을 run `notes`에만 적어 아무도 읽지 않았다(11-06·07·10 '묶음 대비 채점 칸', 11-17 '범위 빼기'). 이제는:
- **연다**: 입력 `asks`에 `{"what": "무엇이 필요한가 — 근거 날짜·건수", "close": "무엇이 되면 닫히나(누가 봐도 확인할 수 있게)"}`. `daily feedback`이 run 줄(feedback:<오늘>)의 `asks` 칸(id `ask:<오늘>:f<번호>`)에 남긴다. 둘 중 하나라도 비면 거절한다. notes에도 한 줄 적어도 되지만 notes만으로는 안 된다.
- **보인다**: 열린 것은 briefing **맨 위** '열린 대화 세션 몫'(저장소 루트 `asks.toml` + run 줄에서 연 것, `python -m market.asks`). 그날 판단에 걸리는 것이면 그 사정대로 하고(예: 아직 없는 칸이면 그 조각 몫을 쓰지 않음) notes에 적는다.
- **닫는다**: 대화 세션이 `asks.toml`에 같은 id로 `status = "닫힘"`, `closed`, `how`를 적는다. 매일 실행은 `asks.toml`을 고치지 않는다.
- 2026-11-17에 닫힌 것: 묶음 대비 채점 칸(`ask:2026-11-06:1` — 조각 주장 `vs = "market"`, `Q_earnings_beat_rel`), 범위 빼기(`ask:2026-11-17:1` — 빼기 대신 `S_comove_market`으로 쪼갠 `Q_rate_up_shift_linked`). 그래서 11-12·13 돌아보기의 '다음엔'(금리 기대 조각을 상관이 작은 종목 1봉에 0.01만, 세 번 엇갈리면 '한 회사'를 빼는 새 버전)은 더 손으로 하지 않는다: 그런 종목에서는 코드가 정한 `S_comove_market = 아니오`로 새 조각이 꺼진다(그 종목에 쓰면 record가 경고한다). briefing 열린 '다음엔'에 남아 있으면 `지난 다음엔 <id> → 안 해 봄 — 2026-11-17 대화 세션이 S_comove_market 조건으로 쪼갬(Q_rate_up_shift_linked)`으로 닫는다.


## 6. 기록
입력 `out/daily/<오늘>/feedback.json`을 채운다: `reviews`(전부), `reading_checks`, `corrections`(있으면), `lessons`, `asks`(있으면), `notes`, **`by`**(이 실행 — 예 "opus-5.5 xhigh(예약 지정값)"), **`summary`**(글 쓰는 실행이 읽을 정리 요약 — 어제·그 전 선택이 어땠고, 무엇을 배워 어떤 뿌리를 새로 세우거나 고치거나 합치거나 내렸는지, 논리집에서 쪼갠·고친 조각, 쉬운 말 두세 문장). 그리고:
```
python -m market.daily feedback out/daily/<오늘>/feedback.json
```
오류가 하나라도 있으면 아무것도 쓰지 않는다 → 고쳐 다시. 하루 한 번(두 번째는 거절).

## 6-1. 일요일: 주간 결산 (이 실행이 쓴다)
일요일이면 6의 기록 뒤에:
```
python -m market.daily report --week     # reports/<오늘>-week.md 뼈대(피드백 정리 줄이 있어야 만든다)
```
- 숫자(표·성적표)는 코드가 채운다 — 고치지 않는다. `[[채울 것: …]]` 자리만 채운다. 문체는 `docs/report-style.md`(1,500~3,000자, "~다/~했다", 전문용어는 처음에 풀어 씀, 범위는 줄표 –, 물결표 금지).
- 구성: 요약, 대상별, 거래와 근거, **반성 n → 바꾼 것·다음엔 → 해 봤더니**(짝으로. 이번 주 '다음엔' 가운데 해 본 것·안 해 본 것·상황이 안 온 것의 수와 대표 하나씩), **이번 주 묶은 뿌리**(늘어난 뿌리, 새 뿌리, 충돌을 가른 조건, 고치거나 합치거나 내린 뿌리, 해 본 처방의 나아짐/모름/나빠짐 — 뿌리 하나에 '해 봄'이 쌓였는데 나빠짐이 나아짐보다 많으면 그 처방을 거둔다고 쓴다), 성적표 변화(손 vs 계산기 vs 이전 버전 vs 기준선, 볼 곳 성적), 다음 주 볼 것.
- 2기 첫 주(2026-11-17 사용자 결정 — 1,000만 원에서 다시 출발)면 그 사실과 1기를 닫은 값을 한 줄.
- `python -m market.daily report --check`가 "일지 점검 통과"여야 커밋한다. 매일 일지(`reports/<오늘>.md`)는 이 실행이 만들지 않는다(09:41 일지 쓰기 실행).
- **10:30 KST 전에 main에 올린다** — 블로그 발행 예약(10:47)이 매일 일지와 주간 결산을 함께 올린다.

## 7. 검사와 커밋·push
```
python -m market.records check
python -m market.logic validate
python -m market.logic audit          # 오류 0이어야 한다
python -m unittest discover -s tests -t .
```
- 하나라도 실패하면 고친다. 기록 파일을 손으로 고치지 않는다. audit 오류가 오늘 고친 논리집 때문이면 고침을 되돌리고(떠 둔 버전 파일은 그대로) 돌아보기 reason에 "고치려 했으나 audit 오류로 미룸".
- **시험·코드가 실패하는데 오늘 기록·논리집은 맞을 때**(2026-11-18 사용자 결정): 검사를 약하게 하지 않는 작은 고침(예: 시험에 박아 둔 값을 등록부·설정에서 읽게 하기)은 이 실행이 해도 된다 — 그 파일을 커밋에 같이 넣고, 무엇을 왜 고쳤는지 마지막 보고에 적는다(알림을 보내면 알림에도). 검사를 빼거나 느슨하게 하는 고침(시험 지우기·건너뛰기·기대값을 결과에 맞춰 넓히기)은 하지 않는다 — 그때는 오늘 고침을 되돌리고, 되돌릴 수 없으면 대화 세션 몫(`asks`)으로 열고 마지막 보고에 적는다.
- 커밋: `git add records knowledge.toml versions places.toml`(일요일엔 `reports/<오늘>-week.md`도, 위 규칙대로 고친 시험·코드 파일도) → `git commit -m "피드백 정리 <오늘>: 돌아보기 <n>건, 뿌리 <같음 n·새 n·충돌 n·고침 n·합침 n·내림 n>, 고친 조각 <id 또는 없음>"`(끝에 빈 줄 다음 `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`) → `git push origin HEAD:main`. 거절되면 `git pull --rebase origin main` 뒤 다시(다른 실행과 다른 파일이라 부딪히지 않는다). `out/`과 매일 일지(`reports/<오늘>.md`)는 넣지 않는다. 일요일엔 기록을 먼저 올리고(일지 쓰기 실행이 그 줄을 기다린다) 주간 결산은 다 쓴 뒤 한 번 더 올려도 된다.

| `market.logic`이 코어를 못 읽음(`proviso/`가 없거나 깨짐) | 논리집 검사 없이 돌아보기·뿌리 묶기만 기록한다. 논리집(knowledge.toml)은 고치지 않는다(검사 없이 고치지 않는다). PROVISO-Nesy에서 꺼내 오지 않고 `asks`로 연다 |
| feedback 입력 오류 | 아무것도 안 써졌다. 오류대로 고쳐 다시 |
| push 실패 | 위 7대로. 그래도 안 되면 `claude/stock-rader-feedback-<오늘>` 브랜치로 push하고 보고 |

## 9. 마지막 보고
짧게: 시작·끝 시각, (일요일) 주간 결산 제목과 올린 시각, 돌아본 예측 수(맞음·틀림과 까닭), 해 본 지난 '다음엔'(해 봄·안 해 봄), 쪼갠·고친 조각(버전), 뿌리(같음·새·충돌·고침·합침·내림 — 새 뿌리 문장), 연 대화 세션 몫, 검사 결과, 커밋 해시와 push한 브랜치. 확인하지 못한 것은 "확인 못 함"으로.
