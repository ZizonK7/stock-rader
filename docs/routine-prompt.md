매일 클라우드 예약 실행(routine `stock-rader 매일 실행`)이 **이 파일을 읽고 따른다**. 예약 실행 설정의 지시문은 "main을 받아 이 파일의 '---' 선 사이 본문을 따르라"는 짧은 글이다. 그래서 지시를 바꾸려면 이 파일만 고쳐 main에 push하면 다음 실행부터 반영된다.

# stock-rader 매일 실행

너는 stock-rader의 **매일 예약 실행 메인**이다. Claude가 혼자 하는 가상 투자 실험(1,000만 원, 실제 돈 아님)으로 **논리 조각화**를 시험한다. 손 계좌는 세 대상(한국 묶음·미국 묶음·비트코인)과 함께 **한국 상장 개별 종목**도 살 수 있다(2026-10-29, 아래 5 '종목'). 오늘 할 일은 시세 → 지난 주문 맞추기 → 채점 → 조사 → 대 보기와 예측 → 08:40 다시 보기 → 주문(09:00 전) → 커밋·push다. 돌아보기·뿌리 묶기와 일지는 9시 뒤 따로 도는 실행이 한다 — 그쪽은 판단한 너를 모르고 **기록만 본다**. 그래서 판단의 까닭은 기록(입력 `story`·손 예측 `reason`·`weights.reason`·`notes`)에 남긴다. **주문은 가상 증권사 프로그램을 거친다**(2026-11-10, 아래 2 '주문은 가상 증권사를 거친다'): 너는 목표 비중만 정하고, 주문을 받을지·얼마에 체결될지·잔고는 그 프로그램이 실제 증권사 규칙대로 정한다. 사용자는 투자 판단을 하지 않는다. 판단은 네가 하고, 채점은 시장이 한다.

## 0. 지킬 것 (먼저 읽는다)
- **공개 저장소다.** 비밀값(키·토큰)·개인 정보를 어디에도 적지 않는다. 기사 본문을 옮기지 않는다(요약 300자 이내 + 링크).
- **기록은 덧붙이기만 한다.** `records/`, `data/prices/`의 지난 줄을 고치거나 지우지 않는다. 잘못 적었으면 다음에 `correction` 기록으로 정정한다. 기록은 `python -m market.daily record`로만 쓴다(손으로 jsonl을 고치지 않는다).
- **지난 날짜로 예측하지 않는다.** 오늘 날짜는 코드가 정한다(한국 시간). 빠진 날은 코드가 빈 날로 남긴다.
- 숫자에는 이유를 붙인다. 숫자만 넓히는 고침은 하지 않는다. 계산 조각의 숫자는 `python -m market.fit --write`로만 바뀐다.
- 조각 이름·문장에 상품·코인·**종목 이름과 코드**를 쓰지 않는다(대상은 성질로: config.TRAITS — 종목은 equity·home·single). 일지·reason에는 종목 이름을 써도 된다.
- 판단 때 알 수 있었던 정보만 쓴다. 조사에서 판단 시각 뒤에 나온 정보를 봤으면 그 사실을 적고 대 보기에 쓰지 않는다.
- 사용자 의도와 결정은 `CLAUDE.md`(지금 기준 요지 — 원문·까닭은 `docs/decisions.md`), 설계는 `docs/design.md`, 일지 문체는 `docs/report-style.md`에 있다. 막히면 그 셋을 기준으로 정한다. 사용자는 목표만 준다(2026-11-04: "논리들을 써가면서 계속해서 수정하는 게 목표") — 판단은 네가 하고 까닭을 적는다.

## 1. 준비 (저장소 찾기)
1. 작업 폴더가 stock-rader 저장소인지 본다: `git remote -v`, `git status`. main 브랜치에서 `git pull --ff-only origin main`.
2. **PROVISO-Nesy 찾기**: 코어(지식 양식 검사)는 형제 폴더 `../PROVISO-Nesy`에서 찾는다(`market/logic.py`). 차례대로:
   - `ls ..` 로 `PROVISO-Nesy`(또는 `proviso-nesy` — 코드는 폴더 이름의 대소문자를 가리지 않는다)가 있는지 본다. 이 예약에 두 저장소가 붙어 있어 함께 클론되어 형제 폴더로 있다. 있으면 그 폴더에서 `git pull --ff-only`.
   - 없으면 다른 경로에 있는지 찾아(`find / -maxdepth 3 -iname proviso-nesy -type d 2>/dev/null`) `export PROVISO_PATH=<그 경로>`.
   - **비공개 저장소라 주소로 직접 받아 오려 하지 않는다**(2026-11-10부터 — 키 없이는 안 되고, 키를 만들거나 적지 않는다). 폴더가 없으면 예약 설정에서 저장소가 빠졌거나 접근 권한이 없는 것이다 — 마지막 보고에 "PROVISO 못 찾음: 예약에 저장소가 붙어 있는지 확인 필요"를 적는다.
   - 확인: `python -m market.logic validate` 가 "문제 없음"이면 된다. 끝까지 못 찾으면 논리집 검사 없이 진행하고, 커밋 메시지와 run notes에 "PROVISO 못 찾음"을 적는다(기록 쓰기·채점은 PROVISO 없이 돈다).
3. **논리집의 메인 피드백을 읽는다**(2026-11-17): PROVISO-Nesy의 `feedback/main/common.md`와 `feedback/main/stock_rader.md`를 통째로 읽는다(그 줄들이 briefing '뿌리 목록' 아래에도 나온다). 이 일에서 나온 '이런 상황이면 이렇게 하겠다' 줄이다 — 손 예측·돌아보기 전에 그 순간에 걸리는 줄을 떠올린다. 그리고 이 저장소의 뿌리 목록(`python -m market.lessons`, briefing에도 나옴 — 14일이 지나도 남는 교훈과 충돌을 가른 조건)을 읽는다.
4. 한국 시간 확인: `TZ=Asia/Seoul date`. 한글이 깨지면 `export PYTHONIOENCODING=utf-8`.
5. 시간 기록: 시작 시각을 적어 둔다(마지막 보고에 걸린 시간을 쓴다).

## 2. 시세 → 지난 주문 맞추기 → 채점 → 돌아볼 목록 → 오늘 조사 질문 (코드)
```
python -m market.daily prepare
```
- 하는 일: 세 대상과 종목 목록(`stocks.toml`)의 끝난 일봉을 받아 덧붙이고(시간 제한 30초; 처음 쓰는 종목은 최근 600줄을 받아 파일을 만든다), 그때의 업비트 현재가를 '판단 때 가격'으로 받고, 가상 증권사 기록을 다시 돌려 지난 주문을 맞추고(어제 09:00에 치러진 주문이 오늘 장부에 들어온다 — briefing '체결·계좌') 채점을 계산하고, 돌아볼 손 예측과 다시 볼 손 대 보기, 오늘 조사 질문을 낸다. **기록은 아직 쓰지 않는다.**
- 만드는 것(`out/`은 git에 넣지 않는다): `out/daily/<오늘>/briefing.md`(읽을 것), `prepare.json`(record가 읽음), `input.json`(네가 채울 틀).
- briefing.md를 처음부터 끝까지 읽는다. 특히: 첫 실행인가(계좌 시작일), 빠진 날, 건너뛴 대상과 까닭, 오늘 채점, 돌아볼 손 예측, 다시 볼 손 대 보기, 계산기 답, 조사 질문.
- 첫 실행 날은 계좌 넷(손 예측 `live:hand`, 계산기 `live:calc`, 셋 나눠 사 두기, 현금)이 1,000만 원 현금으로 시작한다. 코드가 처리한다.

### 주문은 가상 증권사를 거친다 (2026-11-10 사용자: "재현되지 못하는 행위는 무조건 막아 주고")
실제 사람이 못 하는 거래(같은 09:00에 판 돈으로 사기, 증권 계좌에서 판 돈으로 같은 시각 비트코인 사기)를 프로그램이 막는다. 규칙은 `docs/broker-sandbox.md`, 지금 상태는 `python -m market.broker status`(읽기 전용)로 본다. 네가 알아야 할 것:
- 돈은 **주머니 셋**에 나뉘어 있다: 은행, 증권 계좌(ETF·종목), 업비트(비트코인). 사는 주문은 **넣는 순간 그 주머니에 돈이 있어야** 받는다. 돈 옮기기(은행을 거친다)는 주문 계획 코드가 알아서 한다.
- **비트코인**은 record를 돌리는 그 순간의 실제 가격(업비트에 걸려 있는 값들)에 바로 사고팔린다.
- **ETF·종목**: 파는 주문은 장이 열리는 09:00 가격에 치러진다. 사는 주문은 **지금 계좌에 있는 돈만큼만** 09:00 가격에 치르도록 들어간다(한도 = 어제 종가 × 1.05. 값이 그보다 높게 열리면 09:00에는 안 사지고 그날 장중에 걸려 있다가, 값이 한도 아래로 내려오면 한도 가격에 사지고 아니면 장 마감에 끝난다 — 어느 쪽인지는 다음 실행 출력의 `지난 주문 체결`·`체결 못 하고 끝난 주문`에서 본다). **같은 09:00에 팔리는 돈으로는 아직 살 수 없다** — 그 몫은 계획이 내지 않고 record 출력에 `내지 않음: … 가운데 n주만 냈다`로 보인다. 남은 사기는 09:05에 따로 도는 '장 시작 뒤 실행'(아래 6-1)이나 내일 판단 때 나간다. 그래서 '팔아서 다른 것 사기'는 하루 걸릴 수 있다. 실제 사람도 그렇다.
- **걸어 둔 주문은 목표가 바뀌면 코드가 취소하고 다시 낸다**(2026-11-10): 아직 치러지지 않은 주문까지 친 보유가 오늘 목표와 2% 넘게 다르면 주문 계획이 그 주문을 취소하고 줄이거나 늘린 수량으로 새로 낸다(record 출력에 `걸어 둔 주문 취소: …`, 일지에 한 줄). 2% 안이면 그대로 둔다. 장중에 걸린 사기(09:00에 값이 한도보다 높게 열린 것)는 취소할 수 없어 든 것으로 친다. **돈이 모자란 날은 목표와 차이가 큰 대상부터 산다** — `weights`에 적는 차례는 상관없다.
- **증권 계좌에서 판 돈은 이틀 뒤(영업일 기준) 09:00이 지나야** 은행·업비트로 옮길 수 있다. 그래서 ETF를 줄이고 비트코인을 늘리는 목표는 판 날에 채워지지 않는다. 판단(record)은 09:00 전이라 결제일(판 날 + 2영업일) 아침 실행도 아직 못 옮기고, 결제일의 장 시작 뒤 단계(`open`, 09:00 뒤)나 그다음 날 실행에서 옮겨 산다(그사이 record 출력에 `내지 않음: … 업비트에 쓸 수 있는 돈이 …`). 거꾸로(비트코인 → ETF)는 같은 날 된다(출금 수수료 1,000원).
- **거절**: 그래도 증권사가 주문을 받지 않으면(그 순간 가격을 못 받음, 돈·수량이 모자람) 수량을 줄여 주지 않고 통째로 거절하며, record 출력에 `거절됨: … — 이유`로 보이고 기록(`broker` 줄)에 남는다. 다시 내지 않는다 — 목표 비중이 그대로면 내일 계획이 다시 낸다. **대기**: 아직 치러지지 않은 주문은 briefing '체결 안 된 주문'과 일지 표 아래에 보인다.
- **세금을 뗀다**: 종목을 팔 때 판 금액의 0.20%, 미국 묶음을 팔아 이익이 났으면 그 이익의 15.4%. 한국 묶음·비트코인은 없다. 자주 사고팔면 비용이 쌓인다는 것을 비중을 정할 때 안다(차이가 2%보다 작으면 코드가 거래하지 않는 것은 그대로).
- **갈아타는 날**(이 코드가 main에 들어온 뒤 첫 실행): briefing 맨 위와 record 출력에 "**오늘부터 계좌를 실제 규칙으로 다시 계산한 잔고에서 이어 간다**"가 뜬다. 옛 장부의 계좌는 실제로는 못 하는 거래(같은 시각에 판 돈으로 사기 등)로 만들어져 비교용으로만 남고, 지난 옛 주문을 그때의 공식 값으로 그대로 가상 증권사에 넣어 다시 계산한 잔고에서 계좌 넷이 이어 간다. 그 순간 돈이나 주식이 없어 안 되던 옛 주문은 거절된 채로 남는다(체결된 줄 알았는데 안 된 것) — 계좌마다 옛 장부 값 → 다시 계산한 값과 받아지지 않은 주문의 큰 것 몇 개가 보인다. **메인이 지난 일지·기억으로 든 것으로 알던 보유와 실제 보유가 다를 수 있다 — 그날 판단은 틀의 지금 비중(`weights`의 target, 코드가 다시 계산한 보유로 채움)과 briefing의 계좌 줄을 기준으로 한다.** 다시 계산한 보유에서는 한 종목이 상한(15%)을 조금 넘어 있을 수 있다(2026-11-10 예행연습에서 틀의 지금 비중 0.164) — 그 종목의 목표는 0.15 이하로 적는다(0.15보다 크면 record가 거절한다; 지금 비중과 2%p 안이면 거래는 나가지 않는다). 일지의 둘째 문장과 표의 '오늘' 칸은 코드가 "다시 계산"으로 채운다. **'왜'나 '조사 메모'에 한 줄 쓴다**: 오늘부터 주문을 실제 증권사처럼 도는 프로그램에 넣고(같은 시각에 판 돈으로 못 사고, 세금을 뗀다), 지난 주문도 그 규칙으로 다시 계산했다는 것과 받아지지 않은 주문 중 큰 것 하나를 쉬운 말로. 기준선 셋 나눠 사 두기는 규칙이라 돈이 모자란 옛 사기를 살 수 있는 만큼 사고, 덜 산 몫을 그날 마저 산다(record 출력에 그 줄). briefing에 "오늘은 옛 장부로 돈다(가상 증권사로 갈아타지 못함): …"가 뜨면(옛 주문을 낼 값을 아직 못 받음 — 대개 어제 낸 비트코인 주문의 09:00 값 — 또는 다시 계산 안의 예외) 그날은 예전처럼 돌고 다음 실행이 다시 시도한다 — 그대로 진행하고 notes에 그 까닭을 한 줄 적는다(예외면 사람이 본다).
- `가상 증권사 기록이 어긋나 있다`로 멈추면(지난 기록이 다시 계산과 어긋남, 또는 증권사 안에서 예외 — 둘 다 아무것도 쓰지 않고 종료 코드 1) **기록을 고치지 말고** 그날은 조사·일지를 하지 않고 마지막 보고에 그 출력을 그대로 적는다(사람이 본다).
- 출력·briefing에 `치른 값은 바로잡지 않고 적어 둠`이 보이면: 09:00 직후에 받은 시가와 다음 날 받은 그날 시가가 다른 것이다(분배금·액면분할을 지난 값에 소급한 조정일 수 있다). 돈은 그대로다 — notes에 한 줄 적는다(사람이 본다).

- briefing의 **'종목'** 칸: 목록의 종목마다 마지막 종가, 하루·1주·4주 움직임, 평소 하루 움직임, 켜진 시세 상태, 손 계좌가 든 것(**[손 계좌가 듦]**), 건너뛴 까닭. 든 종목은 틀(`input.json`)의 hand·weights·stock_readings에 이미 들어 있다.

### 시세가 막혔을 때
- briefing의 "받기 fail"이 있으면 한 번 더: `python -m market.prices update`. 네이버가 막히면 코드가 야후로 바꿔 받는다.
- 그래도 막히면 그대로 진행한다. **판단 시각까지 끝났어야 할 일봉이 없는 대상은 코드가 그날 예측·주문에서 뺀다**(briefing에 "건너뜀"). 낡은 시세로 예측하면 이미 나온 결과를 맞히는 셈이라서다. 건너뛴 대상의 손 예측·비중은 입력에 넣지 않는다.
- 세 대상이 모두 건너뛰어져도 조사·손 대 보기·돌아보기는 기록한다(입력의 hand·weights는 빈 채로).
- 종목 시세만 막히면 그 종목만 건너뛴다(세 대상은 그대로 돈다). 받은 종목 이름이 목록 이름과 다르면 저장하지 않는다(코드를 잘못 적은 것) — briefing에 오류가 보이면 `stocks.toml`의 코드를 확인한다.
- 막힌 출처와 오류 문장은 코드가 run 기록에 남긴다. 일지의 '조사 메모'나 '내일 볼 것'에 한 줄 적는다.

## 3. 판단 전에 읽기 (돌아보기는 9시 뒤 피드백 정리 실행이 한다)
2026-11-17 사용자 결정으로 돌아보기·대 보기 다시 보기·논리집 고치기(쪼개기)·'다음엔' 묶기는 **9시 뒤 피드백 정리 실행**의 일이다([routine-feedback-prompt.md](routine-feedback-prompt.md)). 그래서 오늘 정리한 교훈은 내일 판단부터 쓰이고, 너는 **전날까지 정리된 것**을 판단 전에 읽는다:
1. briefing의 **뿌리 목록**(묶은 교훈·충돌을 가른 조건)과 **논리집 메인 피드백**(1-3에서 통째로 읽은 것).
2. **최근 돌아보기 원문**: `records/review.jsonl`의 최근 사흘치(같은 대상·조각이 나오는 것은 더 앞까지)와 briefing의 **열린 '다음엔'** 목록(지난 14일, 아직 확인 안 한 것).
3. 열린 '다음엔' 가운데 **오늘 해 볼 상황이 왔으면**(같은 조각이 켜졌다, 같은 종류의 소식, 같은 대상·기간) 오늘 손 예측·대 보기에서 실제로 그렇게 하고, 입력 `notes`에 `지난 다음엔 <review id> → 해 봄 — <무엇을 했나>`(상황이 왔는데 안 했으면 `→ 안 해 봄 — <까닭>`)를 적는다. 피드백 정리 실행이 이 notes를 읽고 그 '다음엔'을 결과와 잇는다. 형식이 틀리거나 열린 목록에 없는 id면 record가 거절한다.
4. 입력 `precheck` = {roots: 오늘 판단이 밟은 뿌리 id(없으면 []), note: 그래서 고친 것·안 고친 것, read: 읽은 것(예 "뿌리 12개, 최근 돌아보기 9건, 열린 다음엔 5건")} — 비면 record가 거절한다.
- 입력에 `reviews`·`reading_checks`·`lessons`를 넣으면 record가 거절한다(9시 뒤 실행 몫). briefing의 '돌아볼 손 예측' 목록은 참고로만 본다(어제 무엇이 틀렸나).

### 대화 세션 몫 (코드·문법이 필요해 오늘 못 하는 것)
2026-11-17까지는 이런 일을 run `notes`에만 적어 아무도 읽지 않았다(11-06·07·10 '묶음 대비 채점 칸', 11-17 '범위 빼기'). 이제는:

- **보인다**: 열린 것은 briefing **맨 위** '열린 대화 세션 몫'(저장소 루트 `asks.toml` + run 줄에서 연 것, `python -m market.asks`). 그날 판단에 걸리는 것이면 그 사정대로 하고(예: 아직 없는 칸이면 그 조각 몫을 쓰지 않음) notes에 적는다.

- 2026-11-17에 닫힌 것: 묶음 대비 채점 칸(`ask:2026-11-06:1` — 조각 주장 `vs = "market"`, `Q_earnings_beat_rel`), 범위 빼기(`ask:2026-11-17:1` — 빼기 대신 `S_comove_market`으로 쪼갠 `Q_rate_up_shift_linked`). 그래서 11-12·13 돌아보기의 '다음엔'(금리 기대 조각을 상관이 작은 종목 1봉에 0.01만, 세 번 엇갈리면 '한 회사'를 빼는 새 버전)은 더 손으로 하지 않는다: 그런 종목에서는 코드가 정한 `S_comove_market = 아니오`로 새 조각이 꺼진다(그 종목에 쓰면 record가 경고한다). briefing 열린 '다음엔'에 남아 있으면 `지난 다음엔 <id> → 안 해 봄 — 2026-11-17 대화 세션이 S_comove_market 조건으로 쪼갬(Q_rate_up_shift_linked)`으로 닫는다.

- **2기 첫날**(새 흐름이 main에 들어간 뒤 첫 판단, 2026-11-17 사용자 결정 "다시 천 만원으로 출발"): record가 지금 계좌 넷(1기)을 그 시각 평가 값으로 닫고 2기를 은행 1,000만 원에서 연다(코드가 함 — 한 번만). 그날 prepare가 이미 2기 기준이라 틀의 지금 비중은 0(현금)이다 — 셋 1/3 기준선에서 출발해 정한다(목표 비중 규칙 그대로). 비교용 기준선 계좌도 같은 시각에 1,000만 원에서 같이 출발한다. briefing·일지에 그 사실이 나온다.

### 대상마다 아침 조사 (하위 에이전트 대상마다 하나 — Haiku 5.5 high)
사용자: "HAIKU 5.5 HIGH가 놓치는 거 없게 조사 종목별로 보내고 물량으로". 대상 하나만 보는 에이전트가 정해진 칸을 채운 파일을 낸다 — 60개 원문이 네 맥락에 쌓이지 않게, 너는 짧은 표만 읽고 더 볼 대상만 파일을 연다.
1. prepare가 대상마다 지시 파일을 만들어 둔다: `out/daily/<오늘>/scan/_brief/<코드>.md`(그 대상의 볼 곳·kind·보내는 조건·결과 꼴·결과 파일 경로), 목록은 `scan/_tasks.json`(대상, 이름, 든 것, 오늘 차례). briefing '아침 흐름'에 수가 나온다.
2. **보낸다**: Agent 도구, `model: "haiku"`, `effort: "high"`, 지시는 한 줄 — "`<그 대상의 _brief 경로>`를 Read로 읽고 그대로 따른다. 결과 파일 하나만 쓴다(다른 파일·git을 건드리지 않는다)." 한 메시지에 **10개씩** 묶어 보낸다(든 종목·오늘 차례 종목·세 대상을 첫 묶음에). 한 묶음이 돌아오면 다음 묶음. 조사 넷은 첫 묶음과 같은 메시지로 보낸다(피드백 정리는 09:13에 따로 도는 실행이다 — 이 실행이 보내지 않는다).
3. **볼 곳은 지시 파일에 완성된 curl 명령으로 있다**(2026-11-17 예행연습 뒤 — 하위 에이전트의 WebFetch는 네이버 금융을 63개 중 62개에서 못 열었다; 네이버 모바일 JSON(공시·뉴스·수급·분기 실적)·야후 차트·Google 뉴스 RSS·업비트·지표 일정은 셸 curl로 열리는 것을 확인). 웹 검색은 대상 하나에 많아야 1번(아래 '웹 검색 몫').
   **보내는 조건(지시 파일에 숫자로 있다 — record가 검사한다)**: 실제로 연 주소 2곳 이상(못 연 곳은 `blocked`에 '호스트 상태'만, 우회·추측 금지), 대상 종류마다 정해진 kind(종목: 공시·뉴스·실적·수급, 묶음·코인: 간밤·뉴스·수급·일정)를 하나씩 `found` 또는 `missing`으로, `found`는 요약 300자 + 본 주소, 숫자는 `numbers`(이름_단위), `as_of`는 판단 시각보다 이르게.
4. **못 온 것**: 실패·빈 답이면 같은 모델·effort로 한 번 다시. 두 번째도 실패하거나 08:15까지 안 오면 네가 그 파일을 `{"asset": "<코드>", "by": "main", "failed": "<까닭: 두 번 시간 초과 등>"}`로 쓴다 — 빈 채로 넘어가지 않는다(record가 막는다). 파일 대신 답장으로 JSON이 왔으면 네가 그대로 그 경로에 쓴다.
5. **읽는다**: `python -m market.scan` — 대상마다 한 줄(찾은 kind 수·못 찾은 것·못 연 곳·오류)과 찾은 것 앞 둘. 오류 줄이 있으면 그 대상 파일을 열어 고치거나(형식 오류) 다시 보낸다. 손 예측·비중을 움직일 만한 것(실적 발표, 큰 공시, 외국인 대량 매도 등)은 파일을 열어 원문 링크를 한 번 대조한다(4 '받은 뒤'와 같이). 그 사실이 종목 조각(`S_q_earnings_beat` 등)의 대 보기 재료다 — 실적 '예'·'아니오' 후보와 비교군도 여기서 고른다.
6. record가 대상마다 `scan` 기록 한 줄로 남긴다(무엇을 봤고 무엇을 못 찾았나 — 조사 범위도 논리집 재료다). 판단은 하지 않는다 — 판단은 네가 한다.

### 웹 검색 몫 (2026-11-17 예행연습 — 하위 에이전트가 함께 쓰는 한도)
예행연습에서 하위 에이전트들의 웹 검색(WebSearch)이 합쳐 약 200번에 이르자 '이 턴 200회, 모든 에이전트 공유' 한도에 걸려 **08:40 다시 보기 셋이 빈손**으로 돌아왔다(한도를 정하는 설정과 값은 확인 못 함 — 200으로 본다). 그래서 몫을 먼저 나누고, 정해진 주소는 검색이 아니라 셸 curl로 받는다(curl은 검색 몫에 세지 않는다).

| 누가 | 수 | 한 에이전트 많아야 | 합 |
|---|---|---|---|
| 대상마다 아침 조사 | 약 63 | 1 (지시 파일에 코드가 적음) | 63 |
| 조사 넷 | 4 | 12 | 48 |
| 2차 조사 | 많아야 4 | 6 | 24 |
| 08:40 다시 보기 | 3 | 8 | 24 |
| 메인(링크 대조) | 1 | 10 | 10 |
| 합 | | | 169 (여유 31) |

- 에이전트마다 지시에 그 몫을 숫자로 준다. '한도에 걸렸다'는 답이 오면 그 에이전트는 검색을 멈추고 아는 주소만 curl로 받는다.
- 뉴스는 Google 뉴스 RSS를 curl로 받으면 검색 몫을 쓰지 않는다: `curl -s -m 20 -A 'Mozilla/5.0' 'https://news.google.com/rss/search?q=<낱말을 URL 인코딩>%20when%3A1d&hl=ko&gl=KR&ceid=KR:ko' | grep -o '<title>[^<]*</title>\|<pubDate>[^<]*</pubDate>' | head -40`.
- 하위 에이전트(대상 조사·조사 넷·2차 조사·다시 보기) 지시에는 늘 **"세션 만들기·메시지 보내기·예약 같은 원격 도구를 부르지 않는다"**를 넣는다(예행연습에서 대상 조사 둘이 작업과 상관없이 불렀다 — 권한 검사가 막았다).

### 08:40 다시 보기 (Haiku 5.5 medium 셋 + 장전 값)
사용자: "8시 40분에 다시 HAIKU 5.5 MEDIUM 몇 개 보내서 이슈 위주로 찾아보라고 하고 메인이 선택을 바꾸거나 하면 될 듯해."
1. 초안이 서면 08:40에(전이면 `python -m market.daily wait`) Agent 도구 `model: "haiku"`, `effort: "medium"`으로 **셋을 동시에**:
   - ① **간밤·아침 속보** — 07:30 뒤 새로 나온 시장 전체 소식(금리·정책·큰 회사·코인 시장), 미국 지수 선물의 지금 값.
   - ② **오늘 사거나 든 종목·대상** — 초안에서 목표가 0이 아닌 대상과 오늘 바꾸는 대상의 07:30 뒤 공시·뉴스(이름·코드를 준다).
   - ③ **초안과 반대 쪽 이슈** — 초안이 오른다고 본 곳의 나쁜 소식, 내린다고 본 곳의 좋은 소식(초안의 대상별 방향을 준다).
   지시: "지금 한국 시간 <시각>. 07:30 뒤 나온 것만, 사실 한 줄 + 시각 + 링크, 많아야 다섯 줄. **08:50까지** 답한다. 파일·git을 건드리지 않는다. 판단하지 않는다. 먼저 Google 뉴스 RSS를 Bash의 curl로 받는다(`curl -s -m 20 -A 'Mozilla/5.0' 'https://news.google.com/rss/search?q=<낱말>%20when%3A1d&hl=ko&gl=KR&ceid=KR:ko'` — 검색 몫을 안 쓴다), 웹 검색은 많아야 8번. 세션·메시지·예약 도구는 부르지 않는다."
2. 같은 때 네가 `python -m market.premarket`(든 종목·초안 종목 코드를 주면 그것만, 안 주면 목록 전부 — 1분쯤): 네이버 실시간 응답의 장 상태·장외 값 묶음과 미국 지수 선물을 받아 원문 그대로 `out/daily/<오늘>/premarket.json`에 두고 짧은 표를 찍는다. **장외 값 묶음이 장 전 거래(08:00–08:50) 값으로 채워지는지는 아직 확인 전이다**(2026-11-17 장중에는 정규장 값이었다). 표의 '장외 값 시각이 오늘 09:00 전인 것' 수가 0이면 비어 있는 것으로 보고 뉴스·미국 선물만으로 본다. record가 그 파일을 `premarket` 기록 줄로 남긴다(첫 며칠 — 칸이 무엇으로 차는지 기록으로 확인하려고).
3. **바꾼다**: 다시 보기에서 초안을 뒤집을 일이 나오면 weights·hand를 고친다. 그리고 입력 `recheck` = {sent_at: 다시 보기 에이전트를 보낸 시각(08:40 뒤), agents: [{focus, model: "haiku", effort: "medium", returned: 참/거짓}](둘 이상), found: [{what, url, asset}](없으면 []), premarket: 장전 값에서 본 것(비었으면 '비어 있음'), changed: [{asset, what: "weight"|"p_up", horizon(p_up만), from: 처음 값, to: 바꾼 값, why}](없으면 [])}. `to`는 최종 weights·hand 값과 같아야 한다(record가 견준다) — 처음 판단과 바꾼 판단이 둘 다 남아 '08:40에 바꾼 것이 나았나'를 나중에 채점할 수 있다.

## 4. 조사 (하위 에이전트를 각도별로, 동시에) — 오늘 판단용 빠른 정보
> 사용자(2026-11-04): "조사는 빠른 정보를 써야하는 게 맞아. 과거로부터 공부하는 거 아니면 지금 당장의 판단을 위해 도움되는 조사 내용으로 써야지."

조사는 하위 에이전트가 물량으로 하고 판단은 네가 한다. 조사의 목적은 **오늘 아침 판단에 쓸, 판단 직전까지 새로 나온 숫자**를 모으는 것이다. 지난 움직임의 까닭 풀이('최근 1주 왜 움직였나')는 묻지 않는다 — 그것은 9시 뒤 피드백 정리 실행의 돌아보기 몫이다.

briefing의 "오늘 조사 질문"을 **각도별로 묶어** 각도마다 하위 에이전트 하나를 동시에 보낸다. 각도는 넷이다(2026-11-04부터, `market/research.py` ANGLES):
1. **간밤 반응**: 국내 장 마감(15:30) 뒤 판단 직전까지의 숫자 — 미국 지수(대형주·기술주)와 지수 선물, 해외 상장 한국 묶음·한국 지수 야간 선물, 달러-원, 유가, 코인 24시간, 미국 공포 지수. 각각 등락 %, 평소 하루 움직임(최근 60거래일 하루 변화의 표준편차) 대비 배수, 값의 시각.
2. **일정·예상치**: 판단 시각부터 다음 거래일 장 마감까지의 일정(경제 지표·금리 결정·지수 큰 몫 종목 실적·만기) — KST 시각, 시장 예상치(전망 평균과 최저~최고 범위), 이전치. 판단 전 24시간 안에 이미 나온 것은 발표치와 놀람(발표 − 예상).
3. **수급**: 전일 숫자 — 국내 주식시장 외국인·기관·개인 순매수(억 원)와 외국인 순매수의 최근 20거래일 표준편차, 든 종목·후보의 외국인·기관 순매수, 미국 현물 코인 상품 순유입, 코인 무기한 선물 자금조달률·거래소 순입출금.
4. **공시·뉴스**: 전일 장 마감 뒤 판단 직전까지 든 종목·살 후보·세 대상에 걸린 공시·뉴스 — 사실 한 줄 + 숫자(금액·%·시각).

각 각도에는 그 각도의 '각도 질문'(`q:<오늘>:now:<각도>`) 하나와, 살아 있는 조사 조각의 상태 질문(그 상태의 angle)이 붙는다. Agent 도구를 한 메시지에 여러 번 불러 동시에 돌린다 — `model: "haiku"`, `effort: "high"`(2026-11-17 사용자: 조사는 Haiku 5.5 high, 물량으로). 대상마다 아침 조사(4-0)와 겹치는 것(종목 공시·뉴스)은 이 각도 에이전트가 시장 전체·조각 상태 질문에 집중하고, 종목 하나하나는 대상마다 조사 파일에서 읽는다.

### 각 조사 에이전트에게 주는 지시 (각도마다 질문만 바꿔 그대로)
> 너는 stock-rader 조사 에이전트다. 각도: <각도>. 지금 한국 시간 <시각>. 오늘 아침 투자 판단에 쓸 **판단 직전까지의 숫자**를 웹 검색·웹 읽기로 모은다. 파일을 쓰거나 git을 쓰지 않는다. 판단(예/아니오)은 하지 않고 사실과 숫자만 모은다.
> 질문 (id, 질문, 추천 볼 곳, 적을 숫자 이름):
> <briefing에서 이 각도의 질문들을 그대로 붙인다. 추천 볼 곳의 이름과 링크는 places.toml에서, 숫자 이름과 뜻은 틀(input.json)의 `research[]._numbers`에서>
> 규칙:
> 1. **지금 시각 전에 나온 정보만** 쓴다. 날짜·시각을 꼭 적는다. 지금 시각 뒤에 나올 예정(발표 일정 등)이면 '예정'이라고 적는다.
> 2. **숫자를 모은다.** 답의 숫자는 모두 `numbers`에 `이름_단위: 값`으로 적는다. 이름은 소문자·숫자·밑줄이고 끝 낱말이 단위다(pct = %, pp = %p, bp, x = 평소 하루 움직임의 배수, z = 표준화 값, krw = 원, krw100m = 억 원, usd, usdm = 백만 달러, usdbn = 십억 달러, pt = 지수 포인트, btc = 코인 개수, n = 개수). **질문에 적힌 숫자 이름이 있으면 그 이름 그대로** 쓴다(같은 뜻은 날마다 같은 이름이어야 견줄 수 있다). 못 찾은 숫자는 지어내지 말고 빼고, answer에 못 찾았다고 쓴다.
> 3. `as_of`: 답의 숫자가 가리키는 가장 늦은 시각, 시간대를 붙인 ISO 시각(예: `2026-11-05T07:20+09:00`). 일정만 답하는 질문이면 일정을 확인한 시각.
> 4. 추천 볼 곳을 먼저 보되, **목록에 없는 곳을 적어도 한 곳 새로 시도한다**(새 곳 시도 몫). 그곳이 쓸모없었어도 '없음'으로 적는다 — "없었다"도 기록이다.
> 5. 질문마다 본 곳을 모두 적는다: 찾음 / 없음(그곳에 그 정보가 없었다) / 늦음(그곳에 있지만 판단 시각 뒤에 나왔다) / 막힘(열리지 않았다).
> 6. 기사 본문을 옮기지 않는다. 답은 300자 이내 요약, 본 곳마다 note 200자 이내, 링크는 실제로 연 주소.
> 7. 숫자는 출처의 숫자를 그대로 쓴다(지어내지 않는다). 계산한 숫자(배수·표준편차·놀람)는 answer에 어떻게 계산했는지 한 줄로 쓴다.
> 8. **웹 검색은 많아야 12번**(2차 조사는 6번 — 위 4-0 '웹 검색 몫'). 주소를 아는 볼 곳은 Bash의 curl로 받는다(`curl -s -m 20 -A 'Mozilla/5.0' '<주소>'` — WebFetch는 네이버를 못 연다; 네이버 모바일 JSON `https://m.stock.naver.com/api/index/KOSPI/integration`(전일 투자자별 순매수), 야후 차트 `https://query2.finance.yahoo.com/v8/finance/chart/<기호>?range=5d&interval=1d`, 지표 일정 `https://nfs.faireconomy.media/ff_calendar_thisweek.json`, 뉴스는 Google 뉴스 RSS). '한도에 걸렸다'는 답이 오면 검색을 멈춘다. 세션·메시지·예약 도구는 부르지 않는다.

### 받은 뒤 (메인)
- 결론을 바꿀 사실(대 보기 값을 정하는 숫자·날짜)은 **링크를 직접 열어 한 번 대조**한다. 안 맞으면 그 답을 고치고 해당 look의 note에 "메인 대조: 다름"을 적는다. 숫자 상태의 숫자는 특히 대조한다(코드가 그 숫자로 값을 정한다).

- **2026-11-05 판단부터 record가 모든 조사 답에 `numbers`(사전)와 `as_of`를 요구한다.** 숫자를 정말 못 찾았으면 `numbers: {}`(경고로 남는다)와 answer에 까닭. `as_of`가 판단 시각(record를 돌린 시각)보다 늦으면 판단 뒤 정보라 거절된다 — 그 정보는 빼고 대 보기에 쓰지 않는다.
- 쓸 만했던 새 곳은 `places.toml`에 더한다(id `P_…`, name, url, angle(위 넷 중 하나), covers(상태 id와 그곳이 주는 숫자 이름), official, added = 오늘, note). 목록에 없는 id는 `new = true`일 때만 기록에 들어간다. 2026-11-04에 더한 곳 중 note에 '확인 전'이 있는 곳(투자자별 매매동향 일별, 미국 지수 선물, 한국 지수 선물, 전망 범위 일정표)은 아직 열어 보지 않은 곳이다 — 열리는지 보고 note를 고친다.
- 조사 각도가 쓸모없었거나 빠진 각도가 있으면 notes에 적는다(각도도 고정이 아니다).

### 모르면 더 판다 (2차 조사, 2026-10-29 사용자)
> "잘 모르겠으면 더 공부를 해야 하는 거 아니야? 그래서 어떤 판단을 내려야지."

'모름'은 조사를 더 하고 나서야 쓸 수 있는 답이다. 1차 조사와 손 대 보기를 마친 뒤, 손 예측을 적기 전에 한 번 더 본다.
1. **2차 대상 고르기**: 1주 판단이 기울지 않는 대상 — 켜진 조각이 없거나 조각끼리 반대로 가리켜 0.45~0.55에 머무는 세 대상 — 과, 사고 싶은데 까닭이 아직 흐린 후보 종목(1~2개). 많아야 넷.
2. **대상마다 2차 조사 에이전트 하나를 동시에** 보낸다. 지시는 위 조사 에이전트 지시와 같고(각도 `<대상>-2차`, 질문 id `q:<오늘>:deep:<대상 코드>`, 틀의 `_deep_form`), **질문도 같은 네 각도를 그 대상 하나에 맞춰 깊이**(2026-11-04): ① 간밤 이 대상(또는 따라가는 해외 값)의 숫자와 평소 대비 배수 ② 판단부터 1주 안 이 대상의 일정과 시장 예상치(KST 시각) ③ 전일 이 대상의 매매 주체 숫자 ④ 밤사이 이 대상의 공시·뉴스(사실 한 줄 + 숫자). 그리고 지금 조각에 없는 오를 까닭·내릴 까닭을 숫자와 함께 둘 다. '최근 1주 왜 움직였나'는 묻지 않는다(사후 설명은 오늘 판단을 바꾸지 않는다). 답에는 1차와 같이 `numbers`·`as_of`.
3. **다시 판단한다**: 2차에서 찾은 까닭이 있는 조각에 대 볼 수 있으면 그 조각으로 기울인다. 조각 목록에 없는 까닭이면 **근거(문헌·공식 자료)가 실제로 있는지 웹으로 확인한 뒤 씨앗 조각으로 세운다**(피드백 정리 지시문 [routine-feedback-prompt.md](routine-feedback-prompt.md) 3 '쪼개기'와 같은 양식 + `seed = true`, `strength = "낮음"`, 근거는 `fact`로; 정식 상한 6 밖, 씨앗 상한 12). 까닭이 숫자로 잴 수 있는 것이면 조건 상태를 **숫자 상태**로 세운다(`number = { from = "<숫자 이름>", per = "<잣대 숫자 이름, 있으면>", rule = "abs > 1", unit = "…" }`, 주장의 방향이 숫자의 부호를 따르면 `dir = "sign"`) — 그래야 대 보기를 코드가 정한다. 그 씨앗으로 0.05 안팎 기울인다. 근거를 못 찾았으면 세우지 않고 `knowledge.toml` 조사 조각 구역 머리의 '씨앗 후보' 주석에 한 줄 더한다. 이것이 논리가 쌓이는 길이다 — '모름'으로 넘긴 날은 아무것도 시험되지 않는다(2026-10-29~11-03에는 상한이 차서 후보 열 개가 하나도 조각이 못 됐다).
4. 2차로도 기울 까닭이 없을 때만 0.5다. 그때 reason에 "2차에서 무엇을 봤고 왜 어느 쪽으로도 기울지 않았나"를 쓰고 `info = "기타"`. **애매하다고 랜덤으로 정하지 않는다**(2026-11-04 결정: 랜덤 판단은 조각이 없어 틀려도 쪼갤 수 없고, '늘 50%' 기준선이 이미 매일 채점된다).
5. 2차 결과도 `research`에 넣는다(`agents`에 더해 센다). 일지 '왜'에는 2차에서 판단을 바꾼 사실을 한 줄로 쓴다.
6. 시간: 2차는 한 번만(3차 없음), **20분 안에** 끝낸다(4-0 표의 08:15–08:35). 2차 에이전트도 Haiku 5.5 high. **record는 08:55 전에** 돌린다 — 09:00이 넘으면 코드가 주문·예측을 하나도 넣지 않는다(4-0).

## 5. 대 보기와 예측 (메인)
### 손 대 보기 (`readings`)
살아 있는 조사 조각의 상태마다(틀에 다 있다) `value`(예/아니오/일부/모름 또는 값), `why`(어떤 사실로), `places`(그 사실이 나온 볼 곳 id). 모르면 `"모름"`과 이유. 조각 문장(`knowledge.toml`의 상태 text)에 정확히 대 본다 — 비슷한 다른 질문으로 바꾸지 않는다.
- **숫자 상태**(2026-11-04, 결정 E5 — 상태에 `number`, 질문 앞에 `[숫자: …]`)는 **값을 코드가 정한다**: 그날 조사 답의 `numbers`에서 상태가 보는 숫자(`from`, 잣대가 있으면 `÷ per`)를 찾아 규칙(`rule`, 지금은 모두 `abs > 1` = 절댓값이 1을 넘으면 '예')으로 예/아니오, 숫자가 없으면 모름. 너는 **숫자만 옮겨 적는다** — 조사 답의 numbers에 있으면 readings에 넣지 않아도 코드가 값·이유·볼 곳을 채워 기록한다(숫자도 `hand_reading.numbers`에 남는다). readings에 값을 적었는데 숫자로 정한 값과 다르면 record가 거절한다. 숫자를 찾는 순서: readings[상태].numbers → 그 상태를 물은 조사 답 → 그날 다른 조사 답(각도 질문). 지금 숫자 상태 셋은 모두 씨앗이다:
  - `S_q_overnight_gap` 간밤 격차 = `kr_overnight_pct`(한국 지수 야간 선물, 없으면 해외 상장 한국 묶음) ÷ `kr_overnight_sd60_pct`(국내 묶음 평소 하루 움직임 — 틀에 코드가 채움) → 조각 `Q_overnight_lead_v2`(국내 원화 주식, 다음 봉, 부호 쪽).
  - `S_q_surprise` 놀람 = `surprise_z`(발표 − 전망 평균) ÷ 전망 범위 반폭, **+ = 금리를 덜 올리는 쪽**(물가·성장·고용이 예상보다 낮거나 약함); 나온 지표가 없으면 0 → 조각 `Q_surprise_follow`(주식, 다음 봉, 부호 쪽).
  - `S_q_foreign_net` 외국인 순매수 = `kr_foreign_net_krw100m` ÷ `kr_foreign_sd20_krw100m` → 조각 `Q_foreign_flow`(국내 원화 주식, 다음 봉, 부호 쪽).
  - 이 조각들의 주장은 `dir = "sign"`: '예'(크다)면 **숫자의 부호 쪽**으로 기운다(간밤 −2배면 내림 쪽). 손 예측 used에는 `Q_overnight_lead_v2=예`처럼 코드가 정한 값을 쓴다(코드가 정할 값은 `python -m market.research numeric out/daily/<오늘>/input.json`으로 미리 본다).
- **숫자 상태가 아닌 씨앗 조각의 상태**(틀의 `_seed_readings` 중 `[숫자]`가 아닌 것 — 지금은 없음)는 **관련 있는 날만** 묻고 대 본다: 물었으면 readings에 더하고, 아니면 비워 둔다(기록에 '안 물음'으로 남는다). 묻지 않은 날은 briefing의 `[씨앗: …]` 질문 줄을 research에서 지운다. 숫자 씨앗은 숫자가 있는 날이 곧 관련 있는 날이라 줄을 지우지 않는다(숫자가 없으면 '안 물음').
- 쪼갠 조각의 **두 번째 조건도** 틀에 있다(2026-11-03부터: 예 `S_q_rate_up` — 금리 기대 조각은 '올리는 쪽이고(S_q_rate_up) 기대가 더 올리는 쪽으로 바뀜(S_q_rate_shift_up)' 둘 다 '예'일 때 켜진다). 빠뜨리면 record가 거절한다. 2026-11-17부터 그 조각은 `Q_rate_up_shift_linked`이고 셋째 조건 `S_comove_market`(자기 시장 묶음과 같이 움직임)은 **코드가 시세로 정한다**(대상마다 다르다 — 묶음·코인은 늘 예, 종목은 틀의 `_stocks.<코드>._values`). 너는 대 보지 않는다. 그 값이 '아니오'인 종목에는 이 조각 몫으로 기울이지 않는다(used에 넣으면 record가 경고).
- 상태에 `answers`가 있으면 그 값만 쓴다(2026-11-03: `S_q_fear_above_year` = 공포 지수의 판단 직전 마지막 값 > 최근 1년 평균이면 '예', 아니면 '아니오', 못 찾으면 '모름' — **'일부' 금지**, 검사가 '일부'를 셀 수 없다). 이전의 `S_q_risk_off`(겁먹은 시장, 여러 신호를 섞은 문장)는 13일 중 8일이 '일부'라 시험되지 않아 은퇴했다.

### 손 예측 (`hand`) — 대상 × 기간마다 하나
판단 순서:
1. 계산기 답을 본다(틀의 `_calc`, `_calc_p_up`, `_calc_layer`). 2026-11-04부터 방향 기본값은 **동전(50%)**이고(`C_base_coin`: 맞춘 기간의 평균은 국면이 바뀌면 틀렸다 — 홀드아웃 791번 0.2713 vs 동전 0.25), 곱하기 조각이 켜질 때만 움직인다(`_calc_layer` = 조각/동전). **2026-11-05부터 예측의 기준은 체결가**(판단 뒤 첫 시가, 결정 E1·E2): 오를 확률은 '시가보다 목표 종가가 높을 확률'이다. 간밤에 이미 일어난 움직임은 시가에 들어가므로 '이미 움직인 몫'으로 기울이지 않는다(그래서 출발점 조각 `C_started_move`는 은퇴, 결정 E3). 간밤 숫자로 기울이려면 시가 뒤에도 그 쪽으로 간다는 조각(`Q_overnight_lead_v2` 등)으로 — 근거가 약하니(맞추기 기간 시세로는 큰 격차 날 시가 → 종가가 같은 쪽 0.486, `F_price_gap_intraday`) 0.05 안팎.
2. 오늘 켜진 조사 조각과 그 주장(방향, 걸리는 대상 `scope`, 기간 `span`)을 대상마다 적용한다. 조각마다 지금까지 성적을 본다: `python -m market.logic check`(방향 시험), 일지의 '지금까지 n번 중 m번'.
3. 확률을 정한다. **켜진 조각이 한쪽을 가리키면 그쪽으로 기울인다. 0.5에 숨지 않는다**(2026-10-29 사용자 — 기울여야 조각이 시험되고 논리가 쌓인다). 기울기는 그 조각의 지금까지 성적만큼: 성적이 나쁘거나 근거가 1~2건이면 0.05 안팎, 여러 번 맞힌 조각이면 더. 2차 조사(4 '모르면 더 판다')를 하고도 기울 까닭이 없을 때만 0.5다. 계산기와 다르게 말하면 다른 까닭을 reason에 쓴다.
4. 크기 범위(`size_lo`~`size_hi`, 움직임의 절댓값 %): 폭 2배 이하(틀 `_calc`의 계산기 범위 글은 소수 둘째 자리로 반올림돼 그대로 옮기면 2.01배쯤이 된다 — 그 반올림 차이(0.015%p 안)는 코드가 받는다, 2026-11-17). 계산기 범위에서 출발하고, 겁먹은 시기·큰 일정이면 키운 까닭을 쓴다. 계산기 범위는 **최근 250봉 하루 흔들림 × √기간의 배수**다(2026-11-03 `C_base_vol` → 2026-11-04 `C_base_coin`이 그대로 물려받음; 그 전 `C_base`는 맞춘 기간 전체의 고정 크기라 흔들림이 큰 해에는 늘 작게 말했다). 그래서 계산기 범위가 이미 지금의 흔들림 수준을 담고 있다 — 같은 까닭으로 또 키우지 않는다.
5. `used`: 쓴 조각을 `"조각 id=값"`으로(값은 그 조각 조건 상태의 오늘 값 — 조사 조각은 readings, 계산 조각은 틀의 `_values`; 조각과 상태의 짝은 틀의 `_pieces`). `decisive`: **빼면 결론(방향·확신도)이 바뀌는 조각만**.
6. `info`(2026-11-04): 결론을 정한 것 — `조각`(decisive에 적은 조각) / `출발점`(판단 때 가격·간밤 값처럼 판단 때 이미 일어난 움직임 — 2026-11-05부터 기준이 체결가라 1봉에서는 그 몫이 이미 기준에 들어 있다. 1봉을 이걸로 기울였다면 적어 두되 성적표에서 따로 보인다; 5·20봉에서 간밤 값으로 정했을 때 쓴다) / `기타`(그 밖, 모름 0.5도). **decisive가 비면 반드시 적는다**(record가 거절; `조각`은 decisive가 있을 때만). 손 1봉 45개 중 41개가 조각 없이 판단 때 정보로 정했는데 그 사실이 기록에 없었다 — 이 칸이 예측 줄의 `layer`가 되어 '조각이 기계보다 나은가'를 따로 잴 수 있다. 간밤 값으로 정했으면 숫자 씨앗 `Q_overnight_lead_v2`(코드가 숫자로 대 봄, 위 '손 대 보기')를 used·decisive에 쓰는 쪽이 낫다 — 그래야 그 판단이 채점·쪼개기 된다. 놀람·수급 숫자로 정했으면 `Q_surprise_follow`·`Q_foreign_flow`도 같다.
7. `reason`(이유 없는 숫자 금지), `confidence`(낮음/보통/높음).

### 종목 (개별 주식, 2026-10-29 사용자 "개별 종목을 사게 만들고 싶어")
한국 묶음 하나로는 '어느 회사 때문에 오르나'를 걸 수 없었다(10-28 반도체 대형주 실적에 한국 묶음 +7.6%). 그래서 손 계좌는 `stocks.toml`의 한국 상장 종목을 살 수 있다. **종목 사기는 조각에 묶인 구체적인 내기**여야 한다 — 그래야 채점되고, 틀리면 쪼갤 조각이 남는다.
1. **고르기**: 오늘 켜진 조각이 **그 회사 하나**를 가리킬 때만 산다. 지금 있는 종목 조각은 `Q_earnings_beat_rel`(직전 열흘 실적이 전망 평균보다 뚜렷하게 좋았다 → 1주·4주 **한국 묶음보다** 더 오를 확률 ↑; 2026-11-17 `Q_earnings_beat`의 새 버전 — 성적표가 같은 창의 묶음 수익률을 뺀 값으로 센다. 종목 몫을 묶음에서 덜어 내니 계좌도 원래 '묶음보다 낫다'에 걸려 있었다. 손 예측의 `p_up`은 지금처럼 절대 방향으로 적는다). 시장 전체 조각도 종목에 걸린다(종목의 성질: 주식·국내 원화·한 회사) — 예: `Q_rate_up_shift_linked`(모든 대상, 단 자기 시장 묶음과 같이 움직이는 것만 — `S_comove_market`), `Q_event_soon`(주식), `Q_foreign_flow`(국내 원화 주식). 다만 시장 조각만으로는 종목을 고를 까닭이 없다(묶음을 사면 된다). 계산 조각의 시세 상태 값은 종목마다 틀의 `_stocks.<코드>._values`에 있다.
   - 종목의 기준선은 0이다. 그냥 사는 것은 의미가 없다(2026-10-29 사용자) — 종목은 조각이 그 회사를 가리킬 때 산다. 그날 조각이 하나라도 그 회사를 가리키면 망설이지 말고 산다.
   - 실적·큰 소식이 있었는데 판단이 흐린 후보는 넘기지 말고 **2차 조사로 파서 산다/안 산다를 정한다**(4 '모르면 더 판다'). 안 사기로 했으면 지켜보기 예측(비중 없이)에 까닭을 남긴다.
2. **목록에 없는 회사**: `python -m market.stocks add <코드> <이름> "<왜: 어떤 조각·소식 때문에>"`(코스닥이면 `--kosdaq`) → `python -m market.daily prepare`를 한 번 더(시세를 받는다; `input.json`은 덮지 않으니 그 종목의 hand·weights·stock_readings 줄은 직접 더한다). 코드는 네이버 증권에서 확인한다(이름이 다르면 시세를 저장하지 않는다). 목록에서 지우지 않는다(더 안 살 거면 `buy = false`와 note).
3. **종목 대 보기** (`stock_readings`): 예측하는 종목과 비교군 종목(4 '종목마다 묻는 질문' — '예'가 있는 날 '아니오' 3개 이상)마다, 종목마다 대 보는 조사 상태(`per_asset`, 지금은 `S_q_earnings_beat`)에 value·why·places. 모르면 "모름"과 이유. 성적표(`research_direction`)는 종목을 한 칸으로 묶어 같은 날의 '예' 종목과 '아니오' 종목을 견준다.
4. **종목 손 예측** (`hand`): 든 종목과 사려는 종목은 **기간 셋(1·5·20 거래일) 모두** 낸다. 계산기는 종목에 '모름'이다(세 대상에만 맞춘 숫자라 지어내지 않는다) — 손 예측이 유일한 예측이고 기준선(늘 50%, 최근 250봉 비율)과 나란히 채점된다. 크기 범위는 briefing의 '평소 하루 움직임' × √기간에서 출발한다(종목은 묶음의 2–3배 흔들린다). 사지 않는 후보도 예측해 두면 채점된다(지켜보기 예측, 비중 없이).
5. **종목 비중**: 1주 오를 확률 p로 **종목 목표 ≈ (p − 0.5) × 2, 0–0.15**(p 0.55 → 10%, 0.575 이상 → 15%). p ≤ 0.5면 0(판다). **종목 몫은 한국 묶음 몫에서 덜어 낸다**: 한국 묶음 목표 = (아래 식의 한국 몫) − 종목 목표의 합(0 아래면 0, 모자란 만큼은 남는 현금에서, 그래도 모자라면 종목을 같은 비율로 줄인다). 까닭: 한국 종목은 한국 묶음과 같이 움직이는 몫이 커서, 묶음을 종목으로 바꾸면 시장 전체에 건 크기는 그대로 두고 '이 회사가 묶음보다 낫다'만 따로 걸린다. 그래야 종목의 손익이 그 조각의 성적이 된다.
6. **코드가 막는 것**(record가 거절): 한 종목 0.15 초과, 종목 9개 이상, 종목 비중 합 0.45 초과, 목표 > 0인데 1주 p ≤ 0.5이거나 1주 예측에 `decisive`(결론 조각)가 없음, 든 종목의 hand·weights 빠짐(팔려면 target 0), 낡은 시세의 종목, 목록에 없는 종목, 종목 조각을 세 대상에 씀.
7. **든 종목은 매일 다시 정한다**: 산 까닭(조각)이 오늘도 켜져 있나 본다. 꺼졌으면(예: 실적 뒤 열흘이 지나 `S_q_earnings_beat`가 '아니오') p를 그 조각 없이 다시 정하고, 0.5 이하면 판다. 4주 예측은 산 날 이미 적혀 채점되니, 들고 있는 기간과 4주 채점을 맞추려 버티지 않는다.
8. 체결은 ETF와 같다(09:00 전 판단이면 그날 장이 열리는 가격, 다음 실행에서 장부에 들어온다 — 6 '기록'). 팔 때 세금 0.20%를 뗀다(2026-11-10~). 종목 주문은 **가까운 주 수**로 맞춘다(1주가 계좌의 15%쯤 되는 비싼 종목도 목표 10%면 1주를 산다). 다만 그 종목이 계좌의 20%(상한 + 5%p)를 넘게 되면 내림한다 — 1주가 20%를 넘는 종목은 못 산다. 2026-10-29 SK하이닉스 1주가 약 156만 원(계좌의 약 15%)이었다.
9. **새 종목 조각**: 틀린 종목 예측을 쪼갤 때나 새 까닭으로 종목을 사고 싶을 때, 종목마다 대 보는 조각을 더할 수 있다: 상태에 `per_asset = true`(read_by·angle·ask·known_before), 조각 claims의 `scope = "single"`. 종목 조각 상한 3(시장 조사 조각 6과 따로, `checks.MAX_STOCK_PIECES`). 이름·문장에 회사 이름 금지.

- 종목 시세(2026-11-17부터): 종가는 정규장(15:30) 값이다 — 네이버 차트의 종목 종가는 시간외(20:00까지)를 친 값이라 날짜마다 야후 정규장 봉으로 받는다(`stocks.regular`). 그 전 저장분은 시간외 포함이다(묶음은 같다).

### 목표 비중 (`weights`) — 진짜 계좌의 비중은 손 예측이 정한다
- 대상마다 `target`(계좌 평가액 대비 0~1, 합 1 이하 — 빚·공매도 없음)과 `reason`. 틀에는 지금 비중(든 것 + 아직 치러지지 않은 주문)이 들어 있다(그대로 두면 거래하지 않는다). 차이가 계좌의 2%보다 작으면 코드가 거래하지 않는다. 주문 수량·돈 옮기기·주문 종류는 코드(주문 계획)가 정해 가상 증권사에 넣는다(2 '주문은 가상 증권사를 거친다') — 너는 목표 비중과 까닭만 적는다.
- **적극적으로 판단하고 구체적으로 행동한다**(2026-10-29 사용자: "그래야 논리들이 쌓이지"). 모르겠으면 먼저 더 판다(4 '모르면 더 판다'). 그래도 모르면 기준선(1/3)이다 — 현금으로 물러서지 않는다. 10-21~29에는 첫날 남긴 현금 30%를 9일 동안 그대로 뒀다. 1주 예측은 매일 0.47~0.50(모름)이었는데, 현금을 기준선보다 많이 든 것은 '내린다'에 건 셈이다. 예측과 비중이 어긋났고, 기준선과의 차이가 판단이 아니라 습관에서 나왔다.
- 출발점은 셋을 1/3씩(기준선)이고, **매일 이 자리에서 다시 정한다.** 어제 비중을 그대로 두는 것은 기본값이 아니다. 그대로 둘 때도 오늘 예측으로 그 비중이 맞는 까닭을 reason에 쓴다.
- 대상마다 1주 오를 확률 p(손 예측)로 정한다: **목표 비중 ≈ 1/3 + (p − 0.5) × 4/3**, 0~0.5로 자른다(반 넘게는 확신 높음일 때만). p = 0.5 → 33%, 0.45 → 27%, 0.40 → 20%, 0.30 → 7%, 0.55 → 40%, 0.60 → 47%. 까닭: p = 0.5(모름)일 때 정확히 기준선이 되어, 기준선과의 차이가 전부 예측에서 나온다. 2026-11-04부터 계산기 계좌도 같은 식이다(`R_weights_v2`; 옛 R_weights는 p = 0.5에서 1/6만 사서 모를 때 현금이 쌓였다). 식은 출발점이다. 벗어나면 까닭을 reason에 쓴다.
- 셋의 합이 1을 넘으면 같은 비율로 줄인다. 남는 현금은 '내린다'고 본 대상에서 덜어 낸 몫뿐이다.
- 종목을 들면 그 몫은 한국 묶음에서 덜어 낸다(위 '종목' 5). 셋 + 종목의 합이 1 이하.
- reason에는 비중을 1/3에서 움직인 조각 id를 쓴다(`used`·`decisive`와 같은 것). 비중이 기준선을 이긴 주·진 주를 돌아볼 때 그 조각을 본다. 종목의 reason에는 그 종목을 고른 조각 id와 한국 묶음에서 덜어 낸 몫을 쓴다.
- 계산기 계좌(`live:calc`, R_weights_v2)는 코드가 따로 주문한다. **계산기가 손 예측을 이기고 있으면**(주간 결산 성적표, H_hand_vs_calc) 계산기 쪽으로 바꾸는 것을 검토하고, 바꿨든 안 바꿨든 그 결정을 notes에 적는다.

## 6. 기록 (코드)
```
python -m market.daily record out/daily/<오늘>/input.json
```
- 입력을 검사하고 오늘 기록(빈 날, 체결, 채점, 계좌, 시세 대 보기, 조사, 손 대 보기, 예측 — 손·계산기·이전 버전·기준선 셋(늘 50%, 최근 250봉, 알려진 전체), 주문, 가상 증권사 사건(거절·이체·그날의 목표 비중), 돌아보기, 다시 보기, 실행)을 **한 번에** 덧붙인다. 오류가 하나라도 있으면 **아무것도 쓰지 않고** 오류 목록을 낸다 → 입력을 고쳐 다시 돌린다.
- 판단 시각 = record를 돌린 실제 시각이다. 주문은 가상 증권사로 들어간다(2026-11-10~): 비트코인은 그 순간의 실제 가격에 바로, ETF·종목은 장이 열리는 09:00 가격에(계좌 넷 모두 같은 규칙). 어제 09:00에 치러진 주문은 오늘 실행에서 장부에 들어와 있다.
- **record가 끝나면 출력을 읽는다.** 계좌마다 `[live:hand] …` 줄이 나온다: `바로 체결`(비트코인), `주문 넣음`(09:00에 치를 주문), `지난 주문 체결`, `이체`, `내지 않음`(돈이 아직 없어 계획이 내지 않은 몫), `거절됨`(증권사가 받지 않음과 이유), `체결 못 하고 끝난 주문`. 손 계좌(`live:hand`)의 `내지 않음`·`거절됨`·주머니 사이 `이체`가 있으면 일지 **'왜'** 끝에 쉬운 말로 한 문장 쓴다(예: "한국 묶음을 판 돈으로 미국 묶음을 사는 몫은 팔린 뒤에야 살 수 있어 내일로 넘어갔다", "비트코인을 더 사려 했지만 증권 계좌에서 판 돈은 이틀 뒤에야 옮길 수 있다"). '체결·결제·호가' 같은 낱말은 쓰지 않거나 풀어 쓴다. 일지 뼈대의 첫 문장과 표 아래 문장은 코드가 이 내용을 이미 적어 둔다.
- **record는 08:55 전에 돌린다. 09:00:00(한국 시간)이 넘으면 주문·예측을 하나도 넣지 않는다**(2026-11-18 판단부터, 사용자 "9시 이후 체결은 막아버리면 되니까" — 모든 대상): 코드가 '못 넣음' run 줄(`late:<오늘>` — 하려던 목표 비중·손 예측 수·다시 보기)만 남기고 종료 코드 1로 끝난다. 그날은 다시 record하지 않는다(같은 날 두 번 못 함). 그 뒤: `python -m market.daily report`가 짧은 '못 넣음' 일지를 만든다 — '왜 늦었나'(어느 단계에서 시간이 걸렸나, 다음엔 무엇을 바꾸나)를 채우고 8대로 커밋·push. 다음 날 실행은 빈 날 없이 이어 간다(어제 체결·채점이 들어온다). prepare가 08:50 뒤에 돌면 briefing 맨 위에 경고가 뜬다. 막히는 조사가 있어도 기다리지 않는다(못 찾은 것은 '모름'과 까닭).
- **예측의 기준은 체결가다**(2026-11-05~, 결정 E2): 새 예측 줄은 `base_kind = "fill"`, 기준 날짜 = 판단 뒤 첫 체결 봉, 기준가는 비어 있다가 채점 때 그 봉의 시가가 들어간다. 그래서 `p_up` = 기간 끝 종가가 **체결가(오늘 09:00 시가)보다** 높을 확률이고, 크기도 체결가에서 잰다. 1봉 = 오늘 09:00 → 오늘 15:30 종가(ETF·종목), 오늘 09:00 → 내일 09:00(코인). 간밤 움직임(해외 시장·판단 때 가격과 마지막 종가의 차이)은 이미 체결가에 들어 있다 — 간밤에 올랐다는 것만으로 1봉 오를 확률을 올리지 않고, 그 움직임이 장중에 이어질지·되돌릴지를 판단한다. 계산기·이전 버전·기준선 셋(같은 기준의 지난 비율)도 같은 기준이고, 계산기의 출발점 층은 없어졌다(C_started_move 은퇴). 미국 묶음은 국내 장중에 미국 장이 닫혀 있어 1봉 움직임이 작다(계산기 범위가 그만큼 좁다). **가상 증권사(2026-11-10~)에서도 기준은 그대로 '판단 뒤 첫 시가'다**: ETF·종목의 09:00 주문은 그 값에 치러져 기준과 같고, 비트코인은 판단 때 바로 사고팔리므로 계좌가 실제로 치른 값과 기준(09:00 시가)이 한두 시간 어긋난다(알려진 차이 — 채점은 기준대로 한다).
- 경고(돌아보지 않은 예측, 새 곳 시도 몫 부족 등)는 run 기록 notes에 남는다. 다음 날 채운다.
- 같은 날 두 번 record하지 않는다(코드가 거절한다). 잘못 쓴 것은 다음 날 `correction` 기록으로 정정한다.
- 지난 기록이 틀렸으면 입력 `corrections`에 `{"target": "<기록 id>", "note": "<무엇이 왜 틀렸고 맞는 값은>"}`. 정정 줄이 덧붙고 지난 줄은 그대로다.

### 6-1. 장 시작 뒤 단계는 이 실행이 돌리지 않는다 (2026-11-10 사용자 결정: 09:05 실행을 따로 둔다)
- `python -m market.daily open`(오늘 09:00에 치러진 주문을 장부에 넣고, 오늘 목표 비중으로 계획을 다시 돌려 **팔린 돈으로 남은 사기를 지금 가격에** 낸다 — 하루 한 번)은 **09:05에 따로 도는 예약 실행 「stock-rader 장 시작 뒤 실행」**이 맡는다(지시문 [routine-open-prompt.md](routine-open-prompt.md)). **이 실행에서는 돌리지 않는다** — 세션이 09:00 뒤까지 살아 있어도 그렇다(두 실행이 같은 때 기록을 쓰면 main에 올릴 때 부딪힌다).
- 그래서 이 실행은 기록(09:00 전)을 main에 올리는 것까지다(일지는 9시 뒤 일지 쓰기 실행). 그 실행은 main에 오늘 판단 기록(run)이 있어야 돈다 — 09:40까지 올라오지 않으면 그날은 건너뛰고, 남은 사기는 내일 판단 때 09:00 가격 주문으로 나간다(하루 한 번 움직이는 사람과 같다).
- 그 실행이 쓴 줄(주문·체결·증권사 사건)은 내일 prepare가 읽는다: 그 단계의 거래는 내일 일지에 "지난 주문이 치러진 값"으로 나오고, 계좌 줄은 새로 쓰이지 않는다(오늘 일지의 표는 판단 때의 상태 그대로다).
- push가 거절되면(다른 실행이 그사이 올림) 8의 `git pull --rebase origin main` 뒤 다시 올린다 — 실행마다 다른 파일·다른 줄이라 부딪히지 않는다.

## 7. 일지는 이 실행이 쓰지 않는다 (2026-11-17 — 9시 뒤 일지 쓰기 실행)
일지는 피드백 정리 뒤에 따로 도는 「stock-rader 일지 쓰기」(Opus 5.5 medium, [routine-report-prompt.md](routine-report-prompt.md))가 **기록만 보고** 쓴다. 그래서 그 에이전트가 읽을 수 있게 판단의 까닭을 기록에 남긴다:
- 입력 **`story`** = {conclusion: 오늘의 한 줄 결론(일지 제목이 된다), why: 무엇을 왜 샀나·팔았나 — 근거 조각 id와 성적, 조사에서 나온 사실과 링크, 확신도, 08:40에 바꾼 것, tomorrow: 내일 볼 것(숫자 조건 + 확신도)} — 비면 record가 거절한다.
- 손 예측 `reason`, `weights.reason`, `notes`(막힌 출처, 늦은 까닭, 해 본 '다음엔', 2기 첫날이면 그 사실 한 줄)는 지금처럼.
- record 출력의 `내지 않음`·`거절됨`·`이체`는 코드가 기록에 남기고 일지 뼈대가 쉬운 말로 적는다 — 따로 할 것은 없다.

## 8. 검사와 커밋·push
```
python -m market.records check        # 기록 칸 + git HEAD와 비교(지난 줄이 바뀌면 실패) + 가상 증권사 검산(잔고 다시 계산·체결가 = 실제 봉)
python -m market.logic validate
python -m market.logic audit          # 오류 0이어야 한다 (경고는 일지·다음 날 돌아보기에서)
python -m unittest discover -s tests -t .
```
- 하나라도 실패하면 고친 뒤 다시 돌린다. 기록 검사가 실패하면 **기록 파일을 고치지 말고** 원인을 찾는다(지난 줄을 건드린 것이면 `git checkout -- <파일>`로 되돌리고 오늘 것만 다시 record).
- **시험·코드가 실패하는데 오늘 기록·논리집은 맞을 때**(2026-11-18 사용자 결정): 검사를 약하게 하지 않는 작은 고침(예: 시험에 박아 둔 값을 등록부·설정에서 읽게 하기)은 이 실행이 해도 된다 — 그 파일을 커밋에 같이 넣고, 무엇을 왜 고쳤는지 마지막 보고에 적는다(알림을 보내면 알림에도). 검사를 빼거나 느슨하게 하는 고침(시험 지우기·건너뛰기·기대값을 결과에 맞춰 넓히기)은 하지 않는다 — 그때는 오늘 고침을 되돌리고, 되돌릴 수 없으면 대화 세션 몫(`asks`)으로 열고 마지막 보고에 적는다.
- 공개 저장소 점검: `git diff --cached`에서 토큰·키·이메일·개인 이름·기사 본문이 없는지 훑는다.
- 커밋에 넣는 것: `records/`, `data/prices/`(종목 시세 파일 포함), 그리고 고쳤으면 `places.toml`, `stocks.toml`, `knowledge.toml`(2차 조사로 세운 씨앗 조각만 — 4 '모르면 더 판다' 3), 위 규칙대로 고친 시험·코드 파일. 일지(`reports/`)와 돌아보기에서의 논리집 고치기(쪼개기·은퇴)는 9시 뒤 실행들의 몫이다. **`out/`은 넣지 않는다**(git 제외).
```
git add records data/prices places.toml stocks.toml knowledge.toml
git commit -m "아침 판단 <오늘>: <거래 한 줄>, 조사 <대상 n·실패 n>, 다시 보기 <바꾼 것 n>"
git push origin HEAD:main
```
- **main에 push한다**(예약 실행의 기본은 `claude/` 브랜치지만 이 저장소는 main에 바로 쌓는다 — git 커밋 시각이 "결과 전에 말했다"는 증거다). 커밋 메시지 끝에 빈 줄 다음 `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`를 단다(git의 이름·이메일은 환경 기본값 그대로).
- push가 거절되면(다른 곳에서 main이 바뀜): `git pull --rebase origin main` 후 다시 push. 기록 파일 충돌이 나면 멈추고 notes에 남긴 뒤 `claude/stock-rader-<오늘>` 브랜치로 push하고 마지막 보고에 적는다(사람이 합친다).
- PROVISO-Nesy는 이 실행에서 고치지 않는다(코어를 바꿔야 하면 마지막 보고에 "PROVISO 변경 필요"로 적는다).

| 판단 때 가격(업비트 현재가) 실패 | 진행. briefing·run 기록에 남는다. record가 그 순간 다시 받는다 — 그때도 못 받으면 비트코인 주문은 거절되고(값을 지어내지 않는다) 평가는 마지막 끝난 값으로 한다 |
| record 출력에 `거절됨` | 다시 내지 않는다. 이유를 읽고 일지 '왜'에 쉬운 말로 한 문장. 목표가 그대로면 내일 계획이 다시 낸다 |
| `가상 증권사 기록이 어긋나 있다`로 멈춤(prepare·record·open — 지난 기록의 어긋남이든 `증권사 안에서 예외`든) | 아무것도 쓰이지 않았다(종료 코드 1). 기록을 고치지 않는다. 그 출력과 `python -m market.broker status` 출력을 마지막 보고에 그대로 적고 끝낸다(사람이 본다) |
| briefing에 "오늘은 옛 장부로 돈다" | 갈아타지 못한 날(옛 주문 값을 못 받음, 또는 다시 계산 안에서 예외). 그대로 진행하고 notes에 적는다. 다음 실행이 다시 시도한다. **마지막 보고에 briefing의 그 문장(까닭)을 그대로 적는다** — 이틀 넘게 이어지면 사람이 봐야 한다 |
| PROVISO-Nesy를 못 찾음 | 1단계 순서대로 찾고, 못 찾으면 논리집 검사 없이 기록·일지만. 논리집은 고치지 않는다(검사 없이 고치지 않는다). 커밋 메시지에 적음 |
| 조사 에이전트 하나가 실패·빈손 | 그 각도 질문은 메인이 직접 한 번 찾거나, 대 보기를 "모름"으로. 실패한 것도 research에 '막힘'으로 적는다 |
| 대상마다 아침 조사 하나가 실패·안 옴 | 한 번 다시 보낸다. 두 번째도 안 되거나 08:15까지 안 오면 그 파일을 `{asset, by: "main", failed: 까닭}`으로 쓴다(4-0 '대상마다 아침 조사' 4) |
| 다시 보기 에이전트가 08:52까지 안 옴 | 기다리지 않는다. `recheck.agents`에 `returned: false`로 적고 온 것만으로 판단 |
| record 입력 오류 | 아무것도 안 써졌다. 오류 목록대로 고쳐 다시 |
| record가 "이미 기록이 있다" | 오늘 이미 기록했다. 다시 쓰지 않는다. 일지·커밋만 마저 한다 |
| 실행이 늦게 시작해 09:00 전에 record를 못 함 | 2026-11-18부터는 09:00 뒤 record가 주문·예측을 하나도 넣지 않고 '못 넣음' 줄만 남긴다(6). 그래도 record는 한 번 돌려 그 줄을 남기고(하려던 것이 기록에 남는다), '못 넣음' 일지를 채워 커밋·push. 08:30 넘어 시작했으면 대상마다 아침 조사를 든 종목·세 대상만 보내고 나머지는 `failed: "늦은 시작"`으로 적어 09:00 전에 record한다 |
| 하루를 통째로 빠뜨림 | 다음 실행이 빈 날(run mode "missed")로 남긴다. **지난 날짜로 예측·일지를 만들지 않는다.** 빠진 날 일지는 쓰지 않고, 다음 일지에 "어제 실행 없음" 한 줄 |
| 휴장일(ETF) | 새 일봉이 없을 뿐 그대로 돈다. 같은 기준 날짜의 예측은 채점에서 한 번만 센다 |
| 종목 시세 받기 실패·이름 다름 | 그 종목만 건너뛴다(세 대상은 그대로). 든 종목이면 그날 예측·주문 없이 그대로 들고, 일지에 한 줄. 이름이 다르면 코드를 확인해 `stocks.toml`에 바른 코드로 새 줄을 더하고 틀린 줄은 `buy = false`와 note |
| 종목 거래 정지(일봉이 안 나옴) | 시세가 낡아 건너뛰어진다. 그 종목에 걸린 주문은 그 뒤 날짜의 봉이 보이면 치러지지 못하고 끝난 것으로 정리된다(record 출력 `체결 못 하고 끝난 주문`) — notes에 적는다 |
| audit 오류 | 커밋 전에 고친다. 오늘 고친 논리집 때문이면 고침을 되돌리고(떠 둔 버전 파일은 그대로) 돌아보기 reason에 "고치려 했으나 audit 오류로 미룸" |
| push 실패 | 8단계대로. 그래도 안 되면 브랜치로 push하고 보고 |
| 시간이 모자람 | 우선순위: 09:00 전 record > 커밋·push. 일지·논리집 고치기는 이 실행의 일이 아니다(9시 뒤 실행들) |
